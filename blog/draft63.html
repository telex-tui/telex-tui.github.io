Option Forgets Why

November 2026

Four strings

Option is Result with the reason thrown away. This post follows four strings through both types, one call at a time, and watches where the reason goes. 

let inputs = ["1", "abc", "", "3"];

"1" and "3" parse. "abc" never will. "" is the interesting one: parse calls it an error, but an empty field often just means nothing was entered. Whether "" is wrong or merely missing is the question the post keeps coming back to.

Reading a trace

Every example in this post comes with a trace: one row per call, one column per input. 

let valid: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();
// .iter()              "1"     "abc"              ""           "3"
//   .parse()         Ok(1)  Err(InvalidDigit)  Err(Empty)    Ok(3)
//   .ok()          Some(1)      None               None    Some(3)
// .filter_map(..)       1                                       3
// .collect()           [1, 3]

Read across a row to see what one call did to every input. Read down a column to follow one input through the chain. Indented rows run inside a closure, here the one passed to filter_map.

Each column lines up on its innermost value, so a value holds still while its wrappers change. Down the "1" column, Ok( becomes Some( around the same 1, and then filter_map unwraps it.

The rest of the notation:

  • A blank cell means the call ran and produced nothing. The gaps in the filter_map row are the failures being dropped.
  • · means the call never ran for that input.
  • Errors show their kind: InvalidDigit is short for ParseIntError { kind: InvalidDigit }.
  • References are left out. .iter() hands out &&str, and the trace shows the string.
  • Labels shorten most arguments to (..). The code above each trace has them in full.
  • When the code is an expression in s rather than a chain, the top row is s and each column is one run of it.
  • A row that starts with or is an alternative to the row above, not the next step.

Forget

.ok() turns a Result into an Option by keeping the value and dropping the reason. .err() keeps the reason and drops the value. 

let value = s.parse::<i32>().ok();    // keep the value, drop the reason
let reason = s.parse::<i32>().err();  // keep the reason, drop the value
// s              "1"        "abc"               ""           "3"
// .parse()     Ok(1)     Err(InvalidDigit)   Err(Empty)    Ok(3)
// .ok()      Some(1)         None                None    Some(3)
// or .err()       None  Some(InvalidDigit)  Some(Empty)       None

Under Result, "abc" and "" fail for different reasons. One .ok() later they are the same None, and nothing downstream can tell them apart. That is the whole post in one row.

.err() is the mirror image, useful when the failures are what you want to collect. It forgets too: the 1 and the 3 become None.

Skip

Both types are collections of zero or one. Iterate Some(x) or Ok(x) and you get one item; iterate None or Err(_) and you get nothing. So flattening drops the failures with no extra code. 

let kept: Vec<i32> = inputs.iter().flat_map(|s| s.parse()).collect();
// .iter()          "1"     "abc"              ""         "3"
//   .parse()     Ok(1)  Err(InvalidDigit)  Err(Empty)  Ok(3)
// .flat_map(..)     1                                     3
// .collect()       [1, 3]

flat_map takes the Result as it is, so there is no .ok(): each Err simply yields no item. filter_map only accepts an Option, which is why the chain in the first trace has to forget before it can skip.

Either way, kept holds no sign of the failures. Not that they happened, not how many, not why.

Stop

Collecting into Result<Vec<_>, _> gives you every value or the first error, and it stops pulling the moment it has that error. 

let all: Result<Vec<i32>, _> = inputs.iter().map(|s| s.parse()).collect();
// .iter()       "1"     "abc"           ·  ·
//   .parse()  Ok(1)  Err(InvalidDigit)  ·  ·
// .collect()         Err(InvalidDigit)

The dots are the point. collect stops at the first Err, so "" and "3" are never parsed, never even taken out of the array. You hear about the first failure and no others.

So a batch comes out one of two ways: 

//    ["1", "3"]             -> Ok([1, 3])
// or ["1", "abc", "", "3"]  -> Err(InvalidDigit)

Option stops in the same place, with the usual loss: 

let all: Option<Vec<i32>> = inputs.iter().map(|s| s.parse().ok()).collect();
// .iter()         "1"     "abc"           ·  ·
//   .parse()    Ok(1)  Err(InvalidDigit)  ·  ·
//   .ok()     Some(1)      None           ·  ·
// .collect()               None

Result tells you why it stopped. Option only tells you that it did.

Reject

Sometimes a value parses and you still do not want it. Option::filter turns a Some into a None when the predicate fails. 

let big = s.parse::<i32>().ok().filter(|&n| n > 1);
// s                "1"       "abc"              ""           "3"
// .parse()       Ok(1)    Err(InvalidDigit)  Err(Empty)    Ok(3)
// .ok()        Some(1)        None               None    Some(3)
// .filter(..)       None      None               None    Some(3)

Three Nones, three different stories: too small, not a number, empty. Nothing in the result says which is which.

Result has no filter at all. It could not have a useful one: rejecting a value means producing an error, and only you know what that error should be. So you name it. 

use std::num::ParseIntError;

#[derive(Debug)]
enum Why {
    Parse(ParseIntError),
    TooSmall(i32),
}

let big = s.parse::<i32>()
    .map_err(Why::Parse)
    .and_then(|n| if n > 1 { Ok(n) } else { Err(Why::TooSmall(n)) });
// s                          "1"            "abc"                     ""          "3"
// .parse()                 Ok(1)         Err(InvalidDigit)         Err(Empty)   Ok(3)
// .map_err(..)             Ok(1)   Err(Parse(InvalidDigit))  Err(Parse(Empty))  Ok(3)
// .and_then(..)  Err(TooSmall(1))  Err(Parse(InvalidDigit))  Err(Parse(Empty))  Ok(3)

Follow the 1. It never moves, but its wrapper goes from Ok( to Err(TooSmall(. The rejection is now a reason like the others, and all four columns end up different.

Fall back

Eventually you want a plain i32. Both types have unwrap_or, and with a fixed fallback they behave the same. 

let n = s.parse::<i32>().unwrap_or(0);
// s                "1"     "abc"              ""         "3"
// .parse()       Ok(1)  Err(InvalidDigit)  Err(Empty)  Ok(3)
// .unwrap_or(0)     1       0                  0          3

The difference shows when the fallback is a closure. Result's unwrap_or_else passes the error in. Option's passes nothing, because it has nothing to pass. 

let n = s.parse::<i32>().unwrap_or_else(|e| { eprintln!("{s:?}: {e}"); 0 });
// stderr: "abc": invalid digit found in string
//         "": cannot parse integer from empty string

let n = s.parse::<i32>().ok().unwrap_or_else(|| { eprintln!("{s:?}: no number"); 0 });
// stderr: "abc": no number
//         "": no number

Both return 0 for the same two inputs. Only the first can say what it papered over.

Decide what "" means

So far "" has been an error, because that is what parse says. For a form field or a config value, empty usually means "not provided", and not provided may be fine. That is an Option decision, made before parsing. 

let n: Result<Option<i32>, _> = (!s.is_empty()).then_some(s).map(str::parse).transpose();
// s                     "1"           "abc"              ""             "3"
// .then_some(s)    Some("1")     Some("abc")              None     Some("3")
// .map(..)       Some(Ok(1))  Some(Err(InvalidDigit))     None   Some(Ok(3))
// .transpose()   Ok(Some(1))       Err(InvalidDigit)   Ok(None)  Ok(Some(3))

then_some turns the empty string into None before anything else happens. map parses only what is there, which leaves an Option around a Result. transpose swaps the two layers: an error inside a Some becomes a plain error, and a None becomes Ok(None).

Watch the "1" column: Some(Ok( becomes Ok(Some( around a 1 that never moves. The type now reads as a sentence: the value may be missing, but it must not be wrong. "abc" is still an error, and "" no longer is.

Require it after all

Then the field becomes mandatory, and the None needs a reason. ok_or supplies one. Add a variant to Why, and a From impl so ? can convert parse errors. 

use std::num::ParseIntError;

#[derive(Debug)]
enum Why {
    Parse(ParseIntError),
    TooSmall(i32),
    Missing,
}

impl From<ParseIntError> for Why {
    fn from(e: ParseIntError) -> Self { Why::Parse(e) }
}

fn required(s: &str) -> Result<i32, Why> {
    let s = (!s.is_empty()).then_some(s).ok_or(Why::Missing)?;
    Ok(s.parse()?)
}
//    required("1")   -> Ok(1)
// or required("abc") -> Err(Parse(InvalidDigit))
// or required("")    -> Err(Missing)
// or required("3")   -> Ok(3)

A function call has one outcome per input, so it gets the or form instead of a trace.

? is where the two types meet head on. In a function that returns Result, it will not take an Option, and the compiler says what to do instead: 

// let s = (!s.is_empty()).then_some(s)?;
// error[E0277]: the `?` operator can only be used on `Result`s, not `Option`s, in a function that returns `Result`
//   use `.ok_or(...)?` to provide an error compatible with `Result<i32, Why>`

One trap remains. It is tempting to reach Why by going through Option: 

let n = s.parse::<i32>().ok().ok_or(Why::Missing);   // don't
// s               "1"     "abc"              ""             "3"
// .parse()      Ok(1)  Err(InvalidDigit)  Err(Empty)      Ok(3)
// .ok()       Some(1)      None               None      Some(3)
// .ok_or(..)    Ok(1)  Err(Missing)       Err(Missing)    Ok(3)

"abc" is not missing. The round trip threw away the real reason and filled in a wrong one. Translate the reason instead of replacing it: 

let n = s.parse::<i32>().map_err(Why::Parse);
// s               "1"           "abc"                     ""          "3"
// .parse()      Ok(1)        Err(InvalidDigit)         Err(Empty)   Ok(3)
// .map_err(..)  Ok(1)  Err(Parse(InvalidDigit))  Err(Parse(Empty))  Ok(3)

Once .ok() has dropped a reason, you can put a reason back, but never the one you lost.

The life of ""

One column, the whole post:

Section Call "" became
Forget .ok() None, from Err(Empty)
Skip .flat_map(..) nothing
Stop .collect() never pulled
Reject .filter(..) None, or Err(Parse(Empty)) with Why
Fall back .unwrap_or(0) 0
Decide .transpose() Ok(None)
Require required(..) Err(Missing)

And the conversions, with what each one does to the reason:

From To Call The reason
Result<T, E> Option<T> .ok() thrown away
Result<T, E> Option<E> .err() kept, and the value is thrown away
Result<T, E> Result<T, F> .map_err(f) translated
Option<T> Result<T, E> .ok_or(e), .ok_or_else(f) supplied by you
Option<Result<T, E>> Result<Option<T>, E> .transpose() kept

Use Option when nobody will ask why. Use Result when someone will. And when you cross from one to the other, read the trace: it shows exactly where the why goes.
