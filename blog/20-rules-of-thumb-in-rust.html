20 Rules of Thumb in Rust

April 2026

Rust has a reputation for a steep learning curve, but a lot of that friction comes from fighting the language instead of working with it. After enough time writing Rust, certain patterns start to feel obvious — not because you memorised a spec, but because you got burned enough times to learn the lesson.

Here are 20 rules of thumb I wish someone had handed me early on.

1. Use String in structs, use &str in function parameters

If a struct holds a string, it should own it — use String. If a function just needs to read a string temporarily, accept &str. This way your struct is self-contained with no lifetime headaches, and your functions stay flexible since both String and &str can be passed as &str. 

struct Config {
    host: String,
}

fn print_host(host: &str) {
    println!("Host: {}", host);
}

2. Prefer borrowing in function parameters over taking ownership

Unless your function actually needs to own the value, take a reference. Taking ownership forces the caller to give up their value or clone it — an unnecessary cost when you only need to read or temporarily modify something. 

// Prefer this
fn get_length(s: &String) -> usize {
    s.len()
}

// Even better — accept &str to be more flexible
fn get_length(s: &str) -> usize {
    s.len()
}

3. If you're cloning frequently to fight the borrow checker, rethink your design

Cloning is a band-aid, not a solution. If you find yourself cloning everywhere to make the compiler happy, it's a sign your ownership structure needs rethinking. Usually the fix is restructuring data flow so one owner is clear, rather than making cheap copies of everything.

4. Don't take &mut T unless you need to mutate

Taking a mutable reference when you only need to read is misleading to callers and unnecessarily restrictive — only one mutable reference can exist at a time. Take &T by default, and only reach for &mut T when mutation is genuinely required.

5. Prefer Vec<T> over arrays unless the size is known and small

Arrays in Rust are fixed-size and live on the stack. That's great for small, known-at-compile-time sizes — but for anything dynamic, Vec<T> is the right tool. When in doubt, start with Vec.

6. Use HashMap by default; switch to BTreeMap only when you need sorted keys

HashMap is faster for most use cases. BTreeMap keeps keys in sorted order and is useful when you need deterministic iteration order or range queries. Don't pay the performance cost of BTreeMap unless ordering is actually a requirement.

7. Wrap primitives in newtypes to prevent mixing up semantically different values

Two f64 values might both represent distance, but one is in metres and the other in miles. The compiler can't catch that bug — but a newtype can. 

struct Metres(f64);
struct Miles(f64);

fn travel(distance: Metres) { /* ... */ }

Now passing a Miles value is a compile-time error. The cost is near-zero; the safety benefit is real.

8. Prefer enum over bool parameters

A function like render(true) tells you nothing at the call site. A function like render(Visibility::Visible) is self-documenting. Booleans are fine for simple flags inside a function, but as parameters they hurt readability. 

// Unclear
fn render(visible: bool) {}

// Clear
enum Visibility { Visible, Hidden }
fn render(visibility: Visibility) {}

9. Use Option for "value might not exist", Result for "operation might fail"

These two types look similar but carry different semantics. Option<T> says "this value is optional — its absence is normal." Result<T, E> says "this operation can fail — here's what went wrong." Mixing them up leads to code that's harder to reason about and error messages that confuse callers.

10. Avoid .unwrap() in production code

.unwrap() panics on None or Err. It's fine during prototyping, but before shipping use .expect("descriptive message") at minimum, so when it panics you know why. Better still, propagate errors properly with ? and a meaningful error type. 

// Avoid in production
let val = some_option.unwrap();

// Better
let val = some_option.expect("config value should always be set");

// Best — propagate the error
let val = some_result?;

11. Define a crate-level Result alias

Writing std::result::Result<T, MyError> everywhere is tedious. Define a type alias at the top of your crate and use it throughout. It's a small thing that makes error-handling code noticeably cleaner. 

// In lib.rs or error.rs
pub type Result<T> = std::result::Result<T, MyError>;

// Now throughout your crate
fn do_thing() -> Result<String> { /* ... */ }

12. Always derive Debug; implement Display for user-facing messages

Debug is for developers — use it in logs, panics, and test output. Display is for end users — use it in error messages and UI output. Derive Debug on nearly everything. Implement Display on types that will be shown to users. 

#[derive(Debug)]
struct MyError {
    message: String,
}

impl std::fmt::Display for MyError {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "Something went wrong: {}", self.message)
    }
}

13. Accept impl Trait in functions instead of concrete types

Using impl Trait in function signatures makes your API more flexible without the complexity of generics syntax. It allows callers to pass any type that implements the trait, and the compiler handles the monomorphisation. 

// Flexible and clean
fn print_all(items: impl Iterator<Item = String>) {
    for item in items {
        println!("{}", item);
    }
}

14. Prefer impl Trait over Box<dyn Trait> unless you need runtime polymorphism

Box<dyn Trait> involves heap allocation and dynamic dispatch — there's a runtime cost. impl Trait is resolved at compile time with zero overhead. Only reach for Box<dyn Trait> when you genuinely need to store mixed types in a collection, or return different types from a single function at runtime.

15. Don't reach for Rc<RefCell<T>> early

Rc<RefCell<T>> is a legitimate tool, but it's often a sign you're trying to work around Rust's ownership model rather than design with it. Before using it, ask whether restructuring your data or rethinking ownership could eliminate the need entirely. Often it can.

16. Prefer iterators over manual for loops

Iterator chains are often more expressive, more composable, and just as fast as manual loops thanks to LLVM optimisation. They also tend to reduce off-by-one errors. 

// Manual loop
let mut doubled = Vec::new();
for x in &numbers {
    if *x > 2 {
        doubled.push(x * 2);
    }
}

// Iterator chain
let doubled: Vec<_> = numbers.iter()
    .filter(|&&x| x > 2)
    .map(|&x| x * 2)
    .collect();

17. Use #[derive] liberally

Rust can auto-generate implementations of common traits for you. There's rarely a reason to hand-write Debug, Clone, PartialEq, or Hash when #[derive] does it correctly and efficiently. Make it a habit to add them upfront. 

#[derive(Debug, Clone, PartialEq, Eq, Hash)]
struct Point {
    x: i32,
    y: i32,
}

18. Make invalid states unrepresentable

This is one of Rust's superpowers. Instead of validating inputs at runtime and hoping you remembered to check everywhere, encode the constraints into your types so invalid states literally cannot be constructed. 

// Runtime validation — easy to forget
fn process(status: &str) {
    if status != "active" && status != "inactive" {
        panic!("invalid status");
    }
}

// Type-level constraint — impossible to pass invalid value
enum Status { Active, Inactive }
fn process(status: Status) { /* always valid */ }

19. Start with the simplest thing that compiles; optimise only after profiling

It's tempting to reach for unsafe, custom allocators, or manual SIMD before you've measured anything. Rust's safe abstractions are highly optimised — idiomatic code is usually fast enough. Write clear code first, profile second, and only optimise the bottlenecks the data shows you.

20. If a function takes more than 3–4 parameters, group them into a struct

Long parameter lists are hard to read, easy to get wrong, and painful to extend. A well-named struct makes call sites self-documenting and gives you a natural place to add validation logic later. 

// Hard to read and error-prone
fn create_user(name: String, email: String, age: u32, is_admin: bool) {}

// Clear and extensible
struct NewUser {
    name: String,
    email: String,
    age: u32,
    is_admin: bool,
}
fn create_user(user: NewUser) {}

Closing thoughts

These rules aren't laws — there are legitimate exceptions to all of them. But they encode the most common lessons that Rust developers learn through trial and error. Follow them by default, and when you break one, make sure you know why.

The goal isn't to write Rust that compiles — it's to write Rust that clearly expresses your intent and is hard to misuse. These rules of thumb point in that direction.
