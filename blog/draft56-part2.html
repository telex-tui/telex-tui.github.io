Inside an Iterator Chain, Part 2: Writing a Step

November 2026

Part 2 of 4 in Inside an Iterator Chain.

Previous: Part 1: How a Chain Runs | Next: Part 3: Beyond One In, One Out

Part 1 took a chain apart. Each step holds the step before it and answers next. This part builds a step from nothing, then turns it into a method you can chain beside the built-ins.

The job is the same as before: 1 to 5, add 1, multiply by 3, subtract 2, then label. No map allowed. By the end we'll have written it anyway.

1. A step is a struct that holds the step before it

An "add" step needs two things: the step it pulls from, and the amount to add.

struct Plus<I> {
    inner: I,
    amount: i32,
}

I is the step this one holds. In our chain, that's the range. But it could be any step at all. The struct itself doesn't care. The next section says what I has to be: an iterator of i32.

2. Its next pulls one value, changes it, and passes it on

impl<I: Iterator<Item = i32>> Iterator for Plus<I> {
    type Item = i32;

    fn next(&mut self) -> Option<i32> {
        let n = self.inner.next()?;
        Some(n + self.amount)
    }
}

These are the two halves of the trip from part 1. The first line is the trip in: ask the step it holds. The second is the trip out: do the job and hand the value on. The ? covers the last trip. When the inner step says None, this one says None too.

The header says when all this works: Plus<I> is an iterator of i32 whenever I is one. If the angle brackets in that line are a blur, Angle Brackets in Rust reads it one bracket at a time.

It already works, called by hand:

let mut step = Plus { inner: 1..=3, amount: 1 };

Calling step.next() four times gives:

Some(2) Some(3) Some(4) None

3. Written as nested structs, the steps come out in reverse

Times and Minus are the same shape as Plus. Here's the whole job, built by hand:

let chain = Minus {
    inner: Times {
        inner: Plus { inner: 1..=5, amount: 1 },
        amount: 3,
    },
    amount: 2,
};

Output, after collect:

[4, 7, 10, 13, 16]

Right answer. Now look at the order. The code starts with Minus and ends with Plus. Yet plus works first, and minus works last. So the steps are written in the opposite order to the one they work in.

Method calls fix that. .plus(1).times(3).minus(2) lists the steps in the order they work.

4. A trait lets you chain the step as a method

You can't add a method to Iterator. It belongs to the standard library. But you can write a trait of your own and implement it for every iterator at once.

trait Steps: Iterator + Sized {
    fn plus(self, amount: i32) -> Plus<Self>
    where
        Self: Iterator<Item = i32>,
    {
        Plus { inner: self, amount }
    }
}

impl<I: Iterator> Steps for I {}

The method just wraps self, the chain so far, in a new Plus. The empty impl gives the method to every iterator there is. Sized is needed because plus takes self by value.

The where line says plus is only for iterators of i32. Keep an eye on that line. It comes back in section 7.

With times and minus added the same way, the chain reads in order:

let out: Vec<i32> = (1..=5).plus(1).times(3).minus(2).collect();
[4, 7, 10, 13, 16]

And ours mix freely with the standard library's:

let out: Vec<i32> = (1..=5).plus(1).map(|n| n * 3).minus(2).take(3).collect();
[4, 7, 10]

5. times and minus are the same shape, copy-pasted

Across the three structs, three impls and three methods, the only real difference is one line:

Some(n + self.amount) // Plus
Some(n * self.amount) // Times
Some(n - self.amount) // Minus

When code repeats like that, the part that changes wants to be a parameter.

6. Pass the change in as a closure

struct Apply<I, F> {
    inner: I,
    f: F,
}

impl<I, F> Iterator for Apply<I, F>
where
    I: Iterator<Item = i32>,
    F: FnMut(i32) -> i32,
{
    type Item = i32;

    fn next(&mut self) -> Option<i32> {
        let n = self.inner.next()?;
        Some((self.f)(n))
    }
}

(self.f)(n) has the extra brackets because self.f(n) would look for a method called f. FnMut lets the closure update anything it captured.

Its trait method follows the same pattern as plus. Now one struct does the job of three:

let out: Vec<i32> = (1..=5)
    .apply(|n| n + 1)
    .apply(|n| n * 3)
    .apply(|n| n - 2)
    .collect();
[4, 7, 10, 13, 16]

7. A step can change the item type

The last job is the label. That step takes an i32 and hands out a String. The struct is the same shape. Only Item changes.

impl<I: Iterator<Item = i32>> Iterator for Label<I> {
    type Item = String;

    fn next(&mut self) -> Option<String> {
        let n = self.inner.next()?;
        Some(format!("#{n:02}"))
    }
}

Item is what this step hands out, so it's what the next step receives.

let labels: Vec<String> = (1..=5).plus(1).times(3).minus(2).label().collect();
["#04", "#07", "#10", "#13", "#16"]

Now put the label too early:

let bad: Vec<i32> = (1..=5).label().plus(1).collect();

The compiler's answer, trimmed:

error[E0271]: expected `Label<RangeInclusive<i32>>` to be an iterator that yields `i32`, but it yields `String`
note: required by a bound in `Steps::plus`

That's the where line from section 4 doing its job. And it's the rule that lets any step slot in anywhere: a step fits after another when its input type is the other step's Item. Nothing else is checked, and nothing else needs to be.

8. Let the closure choose the output type, and you've rebuilt map

Apply only goes from i32 to i32. Loosen both ends. Take whatever the inner step hands out, and hand out whatever the closure returns.

impl<I, F, B> Iterator for Apply<I, F>
where
    I: Iterator,
    F: FnMut(I::Item) -> B,
{
    type Item = B;

    fn next(&mut self) -> Option<B> {
        let item = self.inner.next()?;
        Some((self.f)(item))
    }
}

B is the closure's return type, and it becomes the step's Item. The trait method drops its i32 bound to match:

fn apply<B, F>(self, f: F) -> Apply<Self, F>
where
    F: FnMut(Self::Item) -> B,
{
    Apply { inner: self, f }
}

Now one step does the arithmetic and the label:

let labels: Vec<String> = (1..=5)
    .apply(|n| n + 1)
    .apply(|n| n * 3)
    .apply(|n| n - 2)
    .apply(|n| format!("#{n:02}"))
    .collect();
["#04", "#07", "#10", "#13", "#16"]

That's the chain from part 1, with apply where map was. Put Apply beside the standard library's Map and the real difference is the name. map is a struct that holds the step before it, and a closure.
