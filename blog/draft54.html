What dyn Redacts: Type Erasure in Rust

October 2026

A Vec stores its elements end to end, every one the same size. That's what makes v[i] a single calculation. So how does a Vec<Box<dyn Widget>> hold an 8-byte progress bar next to a 32-byte label?

It doesn't put them next to each other. It holds an array of 16-byte handles, and the values live elsewhere. Type erasure is what makes that work: each handle drops its value's type and keeps exactly what's needed to use the value anyway. This post builds that up from memory layout: why an array needs one size, how the handle gives it one, and what the code on each side of a call still knows.

It builds on Where Your Rust Program Lives: a value's bytes don't contain its functions, and a method is a function that receives the value's address. Every example was compiled with rustc 1.97.0, edition 2024, on x86_64, where an address is 8 bytes. A trait that can be used as dyn is called dyn compatible; older docs and many answers online call it object safe.

1. Why mixed sizes break an array

An array, a slice and a Vec's buffer all store their elements end to end, with nothing between them. To find element i, the compiled code does one calculation:

address of arr[i] = base + i × size_of::<T>()

size_of::<T>() isn't looked up while the program runs. It's a constant, compiled into the instructions, so reaching any element costs one multiplication and one addition. Here are two widgets, and an array of each:

Compiles.

trait Widget {
    fn render(&self) -> String;
}

struct ProgressBar {
    value: u8,
    max: u32,
}

struct Label {
    text: &'static str,
    col: usize,
    row: usize,
}

impl Widget for ProgressBar {
    fn render(&self) -> String {
        format!("[{}/{}]", self.value, self.max)
    }
}

impl Widget for Label {
    fn render(&self) -> String {
        format!("{} at ({}, {})", self.text, self.col, self.row)
    }
}

// Compiled once per W, with size_of::<W>() fixed in each copy
fn show<W: Widget>(name: &str, items: &[W]) {
    println!("{name}: each element is {} bytes", size_of::<W>());
    let base = items.as_ptr() as usize;
    for (i, item) in items.iter().enumerate() {
        let start = item as *const W as usize - base;
        println!("  {name}[{i}] at base + {start}: {}", item.render());
    }
}

fn main() {
    let bars = [
        ProgressBar { value: 7, max: 10 },
        ProgressBar { value: 3, max: 4 },
        ProgressBar { value: 9, max: 9 },
    ];
    let labels = [
        Label {
            text: "CPU",
            col: 0,
            row: 0,
        },
        Label {
            text: "MEM",
            col: 0,
            row: 1,
        },
        Label {
            text: "NET",
            col: 0,
            row: 2,
        },
    ];
    show("bars", &bars);
    show("labels", &labels);
}

Output:

bars: each element is 8 bytes
  bars[0] at base + 0: [7/10]
  bars[1] at base + 8: [3/4]
  bars[2] at base + 16: [9/9]
labels: each element is 32 bytes
  labels[0] at base + 0: CPU at (0, 0)
  labels[1] at base + 32: MEM at (0, 1)
  labels[2] at base + 64: NET at (0, 2)

show is generic, so the compiler makes one copy of it for each type it's used with: one where the element size is 8, one where it's 32. Each copy works on an array of one type, because that type's size is built into the copy's code.

Colours in these pictures: blue is a value's bytes, purple an address that points at a value, orange a vtable, green code, and red something that can't work.

Now put both types in one array, as in the picture's bottom row. Element 1 would start at 32, after the label, but element 2 at 40: no single multiplier gives both. There's no stride to compile, so rustc refuses:

Does not compile.

struct ProgressBar {
    value: u8,
    max: u32,
}

struct Label {
    text: &'static str,
    col: usize,
    row: usize,
}

fn main() {
    let screen = [
        Label {
            text: "CPU",
            col: 0,
            row: 0,
        },
        ProgressBar { value: 7, max: 10 },
        Label {
            text: "MEM",
            col: 0,
            row: 1,
        },

  --> main.rs:19:9
   |

   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ expected `Label`, found `ProgressBar`

Generics don't get around this. show handles bars and labels, but each compiled copy takes one known type, so any one array still holds one type. To hold both, the array needs elements that are all the same size even when the values aren't.

2. The fix: an array of 16-byte handles

A Vec<Box<dyn Widget>> never puts differently sized values side by side. Each value lives in memory of its own, and the array holds a handle to it. Every handle is a fat pointer: two 8-byte words.

  • Word 1, the data pointer: the value's address, wherever it lives: on the stack for &bar, on the heap for a Box.
  • Word 2, the vtable pointer: the address of a small table in read-only data, written by the compiler for one type and one trait. It holds the value's size and alignment, how to drop it, and the address of each trait method's code.

Both words are addresses, so a handle is 16 bytes whether the value behind it is 8 bytes or 1,024. That's the whole trick: the array stores handles, and handles are all one size.

Run the arithmetic again: screen[i] is at base + i × 16. The stride is a constant again, so indexing is the same multiplication and addition as before. Each value keeps its own size and is reached through its handle's word 1.

Compiles.

trait Widget {
    fn render(&self) -> String;
}

struct ProgressBar {
    value: u8,
    max: u32,
}

struct Label {
    text: &'static str,
    col: usize,
    row: usize,
}

impl Widget for ProgressBar {
    fn render(&self) -> String {
        format!("[{}/{}]", self.value, self.max)
    }
}

impl Widget for Label {
    fn render(&self) -> String {
        format!("{} at ({}, {})", self.text, self.col, self.row)
    }
}

fn main() {
    // One handle: two words, whatever it points at
    let bar = ProgressBar { value: 7, max: 10 };
    let w: &dyn Widget = &bar;
    println!("&dyn Widget: {} bytes", size_of::<&dyn Widget>());
    println!("word 1 is bar's address: {}", std::ptr::addr_eq(w, &bar));

    // An array of handles: one stride, whatever each one points at
    let screen: Vec<Box<dyn Widget>> = vec![
        Box::new(Label {
            text: "CPU",
            col: 0,
            row: 0,
        }),
        Box::new(Label {
            text: "MEM",
            col: 0,
            row: 1,
        }),
        Box::new(ProgressBar { value: 7, max: 10 }),
    ];
    println!("each element: {} bytes", size_of::<Box<dyn Widget>>());
    let base = screen.as_ptr() as usize;
    for (i, handle) in screen.iter().enumerate() {
        let start = handle as *const Box<dyn Widget> as usize - base;
        let size = size_of_val(handle.as_ref());
        println!(
            "  screen[{i}] at base + {start}, points at {size} bytes: {}",
            handle.render()
        );
    }
}

Output:

&dyn Widget: 16 bytes
word 1 is bar's address: true
each element: 16 bytes
  screen[0] at base + 0, points at 32 bytes: CPU at (0, 0)
  screen[1] at base + 16, points at 32 bytes: MEM at (0, 1)
  screen[2] at base + 32, points at 8 bytes: [7/10]

The elements sit 16 bytes apart, while the values behind them are 32, 32 and 8 bytes. size_of_val reads each value's size from its vtable, through word 2. There's nowhere else it could come from.

rustc puts the data pointer first and the vtable pointer second, and lays a vtable out as drop, size, alignment, then the methods. That's how rustc does it today; the language doesn't promise either order. A type with nothing to clean up, like these two, gets a null drop slot.

3. Who knows what: the caller and the callee

The handle makes the array uniform, and the price is that code holding a handle no longer knows its value's type. Yet w.render() still prints [7/10], reading fields the caller can't name. That works because the two sides of the call know different things.

The caller: the type is erased

Code holding a &dyn Widget knows only that the value implements Widget. It doesn't know the field names or the layout, it doesn't know the size as a compile-time constant, and it doesn't know which render to call. Ask it for a field and rustc says so:

Does not compile.

trait Widget {
    fn render(&self) -> String;
}

struct ProgressBar {
    value: u8,
    max: u32,
}

impl Widget for ProgressBar {
    fn render(&self) -> String {
        format!("[{}/{}]", self.value, self.max)
    }
}

fn main() {
    let bar = ProgressBar { value: 7, max: 10 };
    let w: &dyn Widget = &bar;
    println!("{}", w.render()); // fine: render was compiled for ProgressBar
    println!("{}", w.value); // the caller doesn't know there is a value
}
error[E0609]: no field `value` on type `&dyn Widget`
  --> main.rs:20:22
   |
20 |     println!("{}", w.value); // the caller doesn't know there is a value
   |                      ^^^^^ unknown field

offset_of!(dyn Widget, value) fails with the same error: there are no offsets to ask about. And because the caller doesn't know which render applies, it can't compile a call to one fixed address. It compiles an indirect call instead: load word 2, load the render slot from that vtable, and call whatever address is there.

The callee: the type was never lost

So how does render read value? The function the vtable points to is <ProgressBar as Widget>::render, compiled like any other method, at a time when ProgressBar was a known type. Its machine code reads max 0 bytes from self and value 4 bytes from it: those offsets are constants in its instructions. All it needs at run time is self, the value's address, and the caller passes word 1 for that.

That's the division of labour. The vtable was filled in when the compiler still knew the type, so its slots lead to code compiled for that type. Nothing else about the type has to survive at run time: just those addresses, the size and the alignment. When the optimizer can see the concrete type, it may turn an indirect call back into a direct one; when it can't, the call goes through the vtable as shown.

What a vtable can hold

The compiler writes every vtable at compile time. The place where &ProgressBar becomes &dyn Widget, called the coercion, is the last place it knows the concrete type, so that's where it picks which vtable word 2 points at. Every slot in that table has to be filled by then. That one rule decides which traits can be used as dyn.

A method with its own type parameter breaks it. Here a widget renders into any writer, and the caller picks the writer type O at each call:

Does not compile.

use std::fmt::Write;

trait Widget {
    fn render_to<O: Write>(&self, out: &mut O);
}

struct ProgressBar {
    value: u8,
    max: u32,
}

impl Widget for ProgressBar {
    fn render_to<O: Write>(&self, out: &mut O) {
        write!(out, "[{}/{}]", self.value, self.max).unwrap();
    }
}

fn main() {
    let bar = ProgressBar { value: 7, max: 10 };
    let w: &dyn Widget = &bar;
    let mut s = String::new();
    w.render_to(&mut s);
}
error[E0038]: the trait `Widget` is not dyn compatible
  --> main.rs:20:17
   |
20 |     let w: &dyn Widget = &bar;
   |                 ^^^^^^ `Widget` is not dyn compatible
   |
note: for a trait to be dyn compatible it needs to allow building a vtable
      for more information, visit <https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility>
  --> main.rs:4:8
   |
 3 | trait Widget {
   |       ------ this trait is not dyn compatible...
 4 |     fn render_to<O: Write>(&self, out: &mut O);
   |        ^^^^^^^^^ ...because method `render_to` has generic type parameters
   = help: consider moving `render_to` to another trait
   = help: only type `ProgressBar` implements `Widget`; consider using it directly instead.

Each O needs its own compiled copy of render_to, just as show needed one copy per type. The vtable would need a slot for every writer type anyone might pass, and O only becomes known at the call, after the table was picked.

There are two ways out, and both are about when O is picked. Put the parameter on the trait, so the dyn type names it: dyn RenderTo<String> picks a vtable with one render_to, for String. Or erase the argument too: a &mut dyn Write is itself a handle, so one compiled render_to serves every writer and fits in one slot.

Compiles.

use std::fmt::Write;

struct ProgressBar {
    value: u8,
    max: u32,
}

// Way out 1: put the parameter on the trait. The dyn type picks it.
trait RenderTo<O: Write> {
    fn render_to(&self, out: &mut O);
}

impl<O: Write> RenderTo<O> for ProgressBar {
    fn render_to(&self, out: &mut O) {
        write!(out, "[{}/{}]", self.value, self.max).unwrap();
    }
}

// Way out 2: erase the argument too. One body serves every writer.
trait Widget {
    fn render_to(&self, out: &mut dyn Write);
}

impl Widget for ProgressBar {
    fn render_to(&self, out: &mut dyn Write) {
        write!(out, "[{}/{}]", self.value, self.max).unwrap();
    }
}

fn main() {
    let bar = ProgressBar { value: 7, max: 10 };
    let mut s = String::new();

    let a: &dyn RenderTo<String> = &bar;
    a.render_to(&mut s);

    let b: &dyn Widget = &bar;
    b.render_to(&mut s);

    println!("{s}");
}

Output:

[7/10][7/10]

Returning Self runs into the wall from the other side:

A caller has to set aside space for a return value before it makes the call. Through a &dyn Widget, duplicate would return 8 bytes for a progress bar and 32 for a label, and the caller can't know which. For both problems there's a fix that keeps the method: where Self: Sized on it takes it out of the vtable, so the trait works as dyn and the method can still be called wherever the concrete type is known.

4. The whole story

  • An array needs one size. Element i is at base + i × size, with the size compiled in, so values of different sizes can't share an array.
  • Type erasure gives it one. The array holds 16-byte handles: a data pointer to the value, wherever it lives, and a vtable pointer. The stride is 16, whatever the values are.
  • The caller loses the type. No field names, no layout, no direct call: it calls through the vtable.
  • The callee keeps it. The method was compiled for the concrete type, with its field offsets built into its instructions. It only needs self.
  • The vtable is fixed before the handle exists. So every method needs one compiled body per type: no type parameters of its own, and no returning Self, unless where Self: Sized takes the method out of the vtable.
