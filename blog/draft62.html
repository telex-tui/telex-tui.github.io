Rust's _or Methods (and Five Other Naming Patterns) in Plain English

November 2026

You open the standard library docs and see unwrap_or, unwrap_or_else, unwrap_or_default, as_ref, to_owned, into_inner, filter_map, take_while, min_by_key, copied, cloned. It looks like a mountain of unrelated methods. It isn't. Just six naming conventions cover roughly 80% of the standard library. Once they click, methods you've never seen before become guessable.

This version adds clarification boxes that answer the question the naming rules leave open: when there are two or three variants, which one do you use? Each box starts with the simplest case, gives the rule, then shows it in assert lines. Paste any box into a #[test] function and it passes.

1. _or vs _or_else -- eager value vs lazy closure

This is the most pervasive. Whenever you see a pair like this, the _or version takes a value you already have. The _or_else version takes a closure that computes the value on demand. Same pattern in unwrap_or / unwrap_or_else, ok_or / ok_or_else, or / or_else. Once you see it once, you see it everywhere. 

let a: Option<i32> = None;

// _or: you already have the fallback value
let x = a.unwrap_or(42);

// _or_else: compute the fallback only if needed
let y = a.unwrap_or_else(|| expensive_default());

The same pairs appear across Option and Result: 

// Option
unwrap_or(val)       / unwrap_or_else(|| ...)
or(other_option)     / or_else(|| ...)

// Result
unwrap_or(val)       / unwrap_or_else(|err| ...)
ok_or(err)           / ok_or_else(|| ...)
or(other_result)     / or_else(|err| ...)

Clarification Start with or: this one, or that one

a.or(b) means "a if it has a value, otherwise b." Both are Options, and so is the result.

assert_eq!(Some(1).or(Some(2)), Some(1));   // has a value: keep it
assert_eq!(None.or(Some(2)), Some(2));      // empty: take the other
assert_eq!(None::<i32>.or(None), None);     // both empty: still None

// You get an Option back, so fallbacks chain
let flag: Option<u16> = None;
let env: Option<u16> = Some(9000);
let file: Option<u16> = Some(7000);
assert_eq!(flag.or(env).or(file), Some(9000));

Clarification Option vs Result: the same or, a different kind of empty

Result works like Option, with one difference: its empty case, Err, carries a reason. None doesn't. That changes two things:

  • or on a Result: keeps the first Ok. If both are Err, you get the second error, and the first one is dropped.
  • The _or_else closure: on Option takes nothing, || ..., because None has nothing to say. On Result it gets the error, |e| ..., so the fallback can depend on what went wrong.
// Option: None says nothing, so the closure takes nothing
let none: Option<u16> = None;
assert_eq!(none.or(Some(2)), Some(2));
assert_eq!(none.or_else(|| "8080".parse().ok()), Some(8080));

// Result: Err says why
let no_flag: Result<u16, &str> = Err("no flag");
let no_env: Result<u16, &str> = Err("no env");
let from_file: Result<u16, &str> = Ok(7000);
assert_eq!(no_flag.or(from_file), Ok(7000));
assert_eq!(no_flag.or(no_env), Err("no env"));    // "no flag" is lost

let r = no_flag.or_else(|e| if e == "no flag" { Ok(8080) } else { Err(e) });
assert_eq!(r, Ok(8080));                          // the closure saw the reason

Clarification unwrap_or: taking the value out

or keeps the wrapper, so you can add more fallbacks. unwrap_or takes the value out, so it ends the chain. The usual shape is to chain with or and unwrap once, at the end. Result is the same, except that its unwrap_or_else gets the error.

let flag: Option<u16> = None;
let env: Option<u16> = None;
assert_eq!(flag.or(env), None);                    // still an Option
assert_eq!(flag.unwrap_or(8080), 8080);            // a plain u16
assert_eq!(flag.or(env).unwrap_or(8080), 8080);    // chain, then unwrap

let r: Result<u16, &str> = Err("timeout");
assert_eq!(r.unwrap_or(500), 500);
assert_eq!(r.unwrap_or_else(|e| if e == "timeout" { 408 } else { 500 }), 408);

// unwrap_or_default: the type's empty value
assert_eq!(flag.unwrap_or_default(), 0);
assert_eq!(None::<String>.unwrap_or_default(), "");

Why bother with the closure version? Because the value in _or is always evaluated, even when it isn't needed. If creating the fallback is expensive -- a heap allocation, a database lookup, a computation -- _or_else avoids the work when the Option is Some or the Result is Ok. 

// This allocates a String every time, even when config has a value:
let name = config.unwrap_or(String::from("default"));

// This only allocates when config is None:
let name = config.unwrap_or_else(|| String::from("default"));

Clarification _or or _or_else: when is the fallback made?

Every _or / _or_else pair differs in exactly one thing: when the fallback gets made.

  • _or(x): x is made first, every time, even when it isn't used. Fine for 8080, "none" or a variable you already have.
  • _or_else(f): f runs only when the fallback is needed. Use it when making the fallback costs something: an allocation, a lookup, a log line.
use std::cell::Cell;

let made = Cell::new(0);
let make = || {
    made.set(made.get() + 1);
    String::from("default")
};

let name = Some(String::from("Ann"));
assert_eq!(name.clone().unwrap_or(make()), "Ann");      // make() ran anyway
assert_eq!(made.get(), 1);
assert_eq!(name.clone().unwrap_or_else(make), "Ann");   // make never ran
assert_eq!(made.get(), 1);
assert_eq!(None.unwrap_or_else(make), "default");       // ran, because it was needed
assert_eq!(made.get(), 2);

Clarification Crossing over: ok_or and .ok()

Going from Option to Result means supplying the reason None doesn't have. Going back throws the reason away.

  • ok_or(e): None becomes Err(e). Use it for a ready-made error, like an enum variant.
  • ok_or_else(f): the same, but the error is only built when needed. Use it when building it allocates, as format! does.
  • .ok(): Ok(v) becomes Some(v), and Err(e) becomes None. The reason is gone.
#[derive(Debug, PartialEq)]
enum ConfigError { Missing }

let port: Option<u16> = None;
let key = "port";
assert_eq!(port.ok_or(ConfigError::Missing), Err(ConfigError::Missing));
assert_eq!(port.ok_or_else(|| format!("missing {key}")), Err(String::from("missing port")));
assert_eq!(Some(8080).ok_or(ConfigError::Missing), Ok(8080));

assert_eq!("8080".parse::<u16>().ok(), Some(8080));
assert_eq!("http".parse::<u16>().ok(), None);   // why it failed is gone

2. as_ vs to_ vs into_ -- how much work is being done

This tells you the cost and the ownership story at a glance:

  • as_ -- a cheap borrow. Just a different view of the same thing. No allocation, no cloning. Think: peeking.
  • to_ -- creates something new but leaves the original alone. Usually involves allocation or conversion. Think: photocopying.
  • into_ -- consumes the original and transforms it. The original is gone. Think: metamorphosing.
let s = String::from("hello");

// as_ -- borrows, cheap, returns a reference
let bytes: &[u8] = s.as_bytes();   // &String -> &[u8], no copy
let slice: &str = s.as_str();     // &String -> &str, no copy

// to_ -- copies/converts, original untouched
let upper: String = s.to_uppercase();  // creates a new String
let owned: String = "hi".to_owned();   // &str -> String, allocates

// into_ -- consumes, original is gone
let bytes: Vec<u8> = s.into_bytes(); // String consumed, Vec reuses its buffer
// println!("{s}");                      // ERROR: s has been moved

as_ is O(1) and virtually free. to_ usually allocates. into_ is often more efficient than to_ because it can reuse the existing buffer instead of copying it.

Clarification as_, to_ or into_?

Pick by what you do with the original next.

  • as_: you only need to read it for now. Same memory, nothing copied.
  • to_: you need your own copy and still need the original. New memory.
  • into_: you're done with the original. It's used up, and its memory is handed over.
let s = String::from("hello");
let buf = s.as_ptr();                  // where the bytes live

let view: &str = s.as_str();           // as_: same memory
assert_eq!(view.as_ptr(), buf);
let copy: String = s.to_owned();       // to_: new memory, s untouched
assert_ne!(copy.as_ptr(), buf);
let bytes: Vec<u8> = s.into_bytes();   // into_: same memory, s is gone
assert_eq!(bytes.as_ptr(), buf);

At a function call: if it takes &str, lend it &s. If it takes a String and you're done with s, pass s. Clone only when you need both.

The pattern repeats across the standard library: 

Path::as_os_str()        // borrow: &Path -> &OsStr
Path::to_path_buf()      // copy:   &Path -> PathBuf
PathBuf::into_os_string() // move:   PathBuf -> OsString

OsStr::as_encoded_bytes() // borrow
OsStr::to_os_string()     // copy
OsString::into_string()   // move

Clarification to_ doesn't always allocate

to_ allocates when it turns something borrowed into something owned, like &str into String. On small Copy types it just returns a new value.

assert_eq!('a'.to_ascii_uppercase(), 'A');   // char in, char out
assert_eq!(258u16.to_be_bytes(), [1, 2]);    // an array, no heap

// &str to String: four spellings, the same result. Use whichever reads best
let a: String = "hi".to_owned();
let b: String = "hi".to_string();
let c: String = String::from("hi");
let d: String = "hi".into();
assert!(a == b && b == c && c == d);

3. _map as a combiner -- two operations in one pass

When a method ends in _map, it performs a transformation as part of another operation. The second word is always map because mapping is the universal glue operation: 

let v = vec![1, 2, 3, 4, 5];

// filter_map = filter + map in one step
// Return Some(value) to keep, None to discard
let evens_doubled: Vec<i32> = v.iter()
    .filter_map(|&x| if x % 2 == 0 { Some(x * 2) } else { None })
    .collect();
// [4, 8]

// find_map = find + map -- find the first match and transform it
let first_even_squared: Option<i32> = v.iter()
    .find_map(|&x| if x % 2 == 0 { Some(x * x) } else { None });
// Some(4)

// flat_map = map + flatten -- map each element to an iterator, then flatten
let words = vec!["hello world", "foo bar"];
let all: Vec<&str> = words.iter()
    .flat_map(|s| s.split_whitespace())
    .collect();
// ["hello", "world", "foo", "bar"]

Clarification map, filter_map or flat_map?

Count what each item turns into.

  • Exactly one: map
  • Zero or one: filter_map: return Some to keep, None to drop
  • Zero or more: flat_map
let lines = ["hello world", "", "foo"];

let lens: Vec<usize> = lines.iter().map(|l| l.len()).collect();
let firsts: Vec<&str> = lines.iter().filter_map(|l| l.split_whitespace().next()).collect();
let words: Vec<&str> = lines.iter().flat_map(|l| l.split_whitespace()).collect();

assert_eq!(lens, [11, 0, 3]);                   // one each
assert_eq!(firsts, ["hello", "foo"]);           // "" has no first word
assert_eq!(words, ["hello", "world", "foo"]);   // "hello world" has two

Clarification filter_map, or filter then map?

Both keep some items and transform them. Pick by whether the test and the transform are the same work.

  • filter_map: the test is the transform. With parsing, you only find out it's a number by parsing it.
  • filter + map: the test is separate. Two small steps read better than an if inside one closure.
let inputs = ["1", "x", "3"];
let nums: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();   // parses once
assert_eq!(nums, [1, 3]);

let v = [1, 2, 3, 4, 5];
let doubled: Vec<i32> = v.iter().filter(|&&x| x % 2 == 0).map(|&x| x * 2).collect();
assert_eq!(doubled, [4, 8]);   // the filter_map example above, easier to read

The pattern works on Option and Result too, not just iterators: 

let maybe_str: Option<&str> = Some("42");

// and_then is Option's version of flat_map:
// map would give Option<Option<i32>>; and_then flattens it to Option<i32>
let parsed: Option<i32> = maybe_str.and_then(|s| s.parse().ok());

Clarification map or and_then?

Look at what your closure returns.

  • A plain value: map
  • An Option: and_then. map would wrap it a second time.
  • On Result: the same pair. The closure for and_then must return the same error type as the Result it's called on.
let s: Option<&str> = Some("42");
assert_eq!(s.map(|s| s.len()), Some(2));                         // plain value: map
assert_eq!(s.map(|s| s.parse::<i32>().ok()), Some(Some(42)));    // Option: map nests it
assert_eq!(s.and_then(|s| s.parse::<i32>().ok()), Some(42));     // and_then doesn't

let r: Result<&str, String> = Ok("42");
assert_eq!(r.and_then(|s| s.parse::<i32>().map_err(|e| e.to_string())), Ok(42));

4. _while adds a predicate

The base method takes a count. The _while variant takes a condition instead. take takes a count, take_while takes a condition. Same for skip vs skip_while: 

let v = vec![1, 2, 3, 4, 5];

// take(n) -- take exactly n elements
let first_three: Vec<&i32> = v.iter().take(3).collect();
// [1, 2, 3]

// take_while(predicate) -- take while condition holds
let small: Vec<&i32> = v.iter().take_while(|&&x| x < 4).collect();
// [1, 2, 3]

// skip(n) -- skip exactly n elements
let after_two: Vec<&i32> = v.iter().skip(2).collect();
// [3, 4, 5]

// skip_while(predicate) -- skip while condition holds
let from_three: Vec<&i32> = v.iter().skip_while(|&&x| x < 3).collect();
// [3, 4, 5]

The pattern is consistent: the base version works with a fixed count, _while makes it dynamic. Crucially, the condition stops being checked at the first false: take_while ends there, and skip_while lets everything after it through, unchecked.

Clarification take, take_while or filter?

On sorted data they often agree. On unsorted data they don't:

  • take(n): you know how many.
  • take_while(f): stop at the first item that fails. Nothing after it is looked at.
  • filter(f): check every item, wherever it is.
  • skip_while(f): drop items until the first that fails, then keep everything after it, unchecked.
let v = [1, 2, 7, 3, 9];
let small = |x: &&i32| **x < 5;

assert_eq!(v.iter().take(2).collect::<Vec<_>>(), [&1, &2]);
assert_eq!(v.iter().take_while(small).collect::<Vec<_>>(), [&1, &2]);       // stops at 7
assert_eq!(v.iter().filter(small).collect::<Vec<_>>(), [&1, &2, &3]);       // finds the 3 too
assert_eq!(v.iter().skip_while(small).collect::<Vec<_>>(), [&7, &3, &9]);   // keeps the 3 anyway

Clarification take_while eats the item that stopped it

To know it should stop, take_while has to take the failing item, and it doesn't give it back. If you need that item, find the split point with position instead.

let v = [1, 2, 7, 3];

let mut it = v.iter();
let head: Vec<&i32> = it.by_ref().take_while(|&&x| x < 5).collect();
assert_eq!(head, [&1, &2]);
assert_eq!(it.next(), Some(&3));   // the 7 is gone

let cut = v.iter().position(|&x| x >= 5).unwrap_or(v.len());
assert_eq!(v.split_at(cut), (&[1, 2][..], &[7, 3][..]));   // nothing lost

// map_while: transform until the first None
let nums: Vec<i32> = ["1", "2", "x", "4"].iter().map_while(|s| s.parse().ok()).collect();
assert_eq!(nums, [1, 2]);

5. _by / _by_key -- "by what measure?"

The base method uses natural ordering (Ord). The _by variant lets you supply a custom comparator. The _by_key variant lets you say "compare by this extracted value": 

let words = vec!["cherry", "fig", "apple", "date"];

// min() -- natural ordering (alphabetical for strings)
let first = words.iter().min();
// Some("apple")

// min_by -- custom comparator
let shortest = words.iter()
    .min_by(|a, b| a.len().cmp(&b.len()));
// Some("fig")

// min_by_key -- compare by extracted key (simpler when you can)
let shortest = words.iter()
    .min_by_key(|w| w.len());
// Some("fig")

The same trio appears for max, sort, and others: 

// Sorting
v.sort();                          // natural order
v.sort_by(|a, b| b.cmp(a));        // custom comparator (here: reverse)
v.sort_by_key(|item| item.score);   // compare by extracted field

// Max
v.iter().max();                     // natural order
v.iter().max_by(|a, b| ...);       // custom comparator
v.iter().max_by_key(|x| ...);      // compare by extracted key

Use _by_key for comparing a single property or derived value. Use _by for complex logic, such as multi-field tie-breaking or custom sort orders.

Clarification _by_key or _by?

Start with _by_key. Switch to _by when the key can't be handed back on its own.

  • _by_key: one value decides the order. Several values? Return a tuple. Reversed? Wrap it in Reverse.
  • _by: the comparison needs both items at once: floats (f64 isn't Ord, so use total_cmp), or a key that borrows from the item.
use std::cmp::Reverse;

let mut scores = vec![("bo", 90), ("al", 90), ("cy", 70)];
scores.sort_by_key(|&(name, score)| (Reverse(score), name));   // score high to low, then name
assert_eq!(scores, [("al", 90), ("bo", 90), ("cy", 70)]);

let mut times = vec![2.5_f64, 0.5, 1.0];
// times.sort_by_key(|t| *t);   // error[E0277]: the trait bound `f64: Ord` is not satisfied
times.sort_by(|a, b| a.total_cmp(b));
assert_eq!(times, [0.5, 1.0, 2.5]);

struct User { name: String }
let mut users = [User { name: "bo".into() }, User { name: "al".into() }];
// users.sort_by_key(|u| &u.name);   // error: lifetime may not live long enough
users.sort_by(|a, b| a.name.cmp(&b.name));
assert_eq!(users[0].name, "al");

Clarification Ties, stability and sort_by_cached_key

When items compare equal, the variants behave differently:

  • sort, sort_by_key: stable: equal items keep the order they started in.
  • sort_unstable*: often faster, but equal items may swap.
  • max_by_key / min_by_key: on a tie, max returns the last of the equals and min the first.
  • sort_by_cached_key: computes each key once. Use it when the key is costly, like to_lowercase. For a plain field, sort_by_key is likely faster.
let mut words = vec!["bb", "a", "cc", "d"];
words.sort_by_key(|w| w.len());
assert_eq!(words, ["a", "d", "bb", "cc"]);   // "a" before "d", as they started

let words = ["bb", "a", "cc", "d"];
assert_eq!(words.iter().max_by_key(|w| w.len()), Some(&"cc"));   // the last of the longest
assert_eq!(words.iter().min_by_key(|w| w.len()), Some(&"a"));    // the first of the shortest

let mut names = vec!["bo", "Al", "cy"];
names.sort_by_cached_key(|n| n.to_lowercase());   // one to_lowercase per name
assert_eq!(names, ["Al", "bo", "cy"]);

6. copied vs cloned -- how expensive is the copy?

Both do the same thing: turn an iterator of references into an iterator of owned values. Same idea (get an owned value from a reference), but copied is for small cheap types and cloned is for anything: 

let v = vec![1, 2, 3];

// copied -- requires T: Copy (small, cheap types: integers, bools, floats)
let owned: Vec<i32> = v.iter().copied().collect();

// cloned -- requires T: Clone (anything, but might be expensive)
let owned: Vec<i32> = v.iter().cloned().collect();

Both work here because integers implement both Copy and Clone. The difference matters for intent and guarantees: 

let strings = vec![String::from("a"), String::from("b")];

// strings.iter().copied()  -- WON'T COMPILE: String isn't Copy
let owned: Vec<String> = strings.iter().cloned().collect(); // works

If it compiles with copied, prefer it. It signals to the reader that the copy is trivial -- a memcpy of a few bytes, not a heap allocation. When you see cloned, you know something more expensive might be happening.

Clarification copied, cloned, into_iter, or nothing?

First ask whether you need owned values at all.

  • Only reading: keep the references. Nothing is copied.
  • Owned, and the items are Copy: copied.
  • Owned, anything else, and you keep the collection: cloned, or to_vec() for the whole thing.
  • Done with the collection: into_iter. The items move out; nothing is cloned.
let strings = vec![String::from("a"), String::from("b")];
let buf = strings[0].as_ptr();

let r: &String = &strings[0];                             // a reference: the same String
assert_eq!(r.as_ptr(), buf);
let c: Vec<String> = strings.iter().cloned().collect();   // cloned: new Strings
assert_ne!(c[0].as_ptr(), buf);
let m: Vec<String> = strings.into_iter().collect();       // into_iter: moved, not copied
assert_eq!(m[0].as_ptr(), buf);

assert_eq!([10, 20].first().copied(), Some(10));          // copied works on Option<&T> too

Putting it all together

These six conventions are composable. You can predict method names you've never seen:

  • ok_or_else -- converts Option to Result, computing the error lazily (_or_else = closure)
  • into_keys -- consumes a HashMap and gives you owned keys (into_ = consuming)
  • max_by_key -- finds the maximum by an extracted value (_by_key = extracted comparison)
  • to_ascii_uppercase -- creates a new value, leaves the original (to_ = new allocation)

When you encounter a new type in the standard library, you can often guess what methods it has. Does it have as_ref? Probably. Does it have into_inner? If it wraps something, yes. Does the iterator adapter have a _by_key variant? Check, but likely.

The naming isn't arbitrary. It's a system. Learn these six meta-patterns and the standard library stops feeling like a phone book and starts feeling like a language you can read.
