Rust's _or Methods (and Five Other Naming Patterns) in Plain English

November 2026

You open the standard library docs and see unwrap_or, unwrap_or_else, unwrap_or_default, as_ref, to_owned, into_inner, filter_map, take_while, min_by_key, copied, cloned. It looks like a mountain of unrelated methods. It isn't. Just six naming conventions cover roughly 80% of the standard library. Once they click, methods you've never seen before become guessable.

This version adds clarification boxes that answer the question the naming rules leave open: when there are two or three variants, which one should you use? Each box gives the rule of thumb, then shows it in code. They're mostly assert lines, so the expected result is part of the code: paste any box into a #[test] function and it passes.

1. _or vs _or_else -- eager value vs lazy closure

This is the most pervasive. Whenever you see a pair like this, the _or version takes a value you already have. The _or_else version takes a closure that computes the value on demand. Same pattern in unwrap_or / unwrap_or_else, ok_or / ok_or_else, or / or_else. Once you see it once, you see it everywhere. 

let a: Option<i32> = None;

// _or: you already have the fallback value
let x = a.unwrap_or(42);

// _or_else: compute the fallback only if needed
let y = a.unwrap_or_else(|| expensive_default());

The same pairs appear across Option and Result: 

// Option
unwrap_or(val)       / unwrap_or_else(|| ...)
or(other_option)     / or_else(|| ...)

// Result
unwrap_or(val)       / unwrap_or_else(|err| ...)
ok_or(err)           / ok_or_else(|| ...)
or(other_result)     / or_else(|err| ...)

Why bother with the closure version? Because the value in _or is always evaluated, even when it isn't needed. If creating the fallback is expensive -- a heap allocation, a database lookup, a computation -- _or_else avoids the work when the Option is Some or the Result is Ok. 

// This allocates a String every time, even when config has a value:
let name = config.unwrap_or(String::from("default"));

// This only allocates when config is None:
let name = config.unwrap_or_else(|| String::from("default"));

Clarification Which one to use: unwrap_or, unwrap_or_else or unwrap_or_default

Ask what the fallback costs to make. Use unwrap_or when it's a literal, a small Copy value or a variable you already have. Use unwrap_or_else when making it calls a function: an allocation, a lookup, anything with a side effect. Use unwrap_or_default when the fallback is just the type's empty value, like 0, "" or an empty Vec.

use std::cell::Cell;

let calls = Cell::new(0);
let fallback = || {
    calls.set(calls.get() + 1);
    String::from("default")
};

let config = Some(String::from("custom"));
assert_eq!(config.clone().unwrap_or(fallback()), "custom");    // fallback() ran anyway
assert_eq!(calls.get(), 1);
assert_eq!(config.clone().unwrap_or_else(fallback), "custom"); // the closure was never called
assert_eq!(calls.get(), 1);

// A cheap fallback: unwrap_or is fine, and shorter
let port: Option<u16> = None;
assert_eq!(port.unwrap_or(8080), 8080);

// The empty value: unwrap_or_default says exactly that
let name: Option<String> = None;
let count: Option<usize> = None;
assert_eq!(name.unwrap_or_default(), "");
assert_eq!(count.unwrap_or_default(), 0);
assert_eq!(String::new().capacity(), 0);   // and String::new() doesn't allocate

Clarification The same rule for ok_or and or, plus one more reason for _or_else

On a Result, the _or_else closure gets the error, so use it whenever the fallback depends on what went wrong. For ok_or, a plain enum variant is cheap, but an error built with format! allocates, so that one belongs in ok_or_else. In a chain of or_else fallbacks, each lookup runs only if the ones before it came up empty.

use std::cell::RefCell;

// The fallback can look at the error
let r: Result<u16, String> = Err(String::from("timeout"));
let status = r.unwrap_or_else(|e| if e == "timeout" { 408 } else { 500 });
assert_eq!(status, 408);

// ok_or with a ready-made error, ok_or_else with one that has to be built
#[derive(Debug, PartialEq)]
enum ConfigError { Missing }
let key = "port";
let missing: Option<u16> = None;
assert_eq!(missing.ok_or(ConfigError::Missing), Err(ConfigError::Missing));
assert_eq!(missing.ok_or_else(|| format!("missing {key}")), Err(String::from("missing port")));

// A fallback chain: later lookups run only when needed
let tried = RefCell::new(Vec::new());
let lookup = |source: &'static str, found: Option<u16>| {
    tried.borrow_mut().push(source);
    found
};
let port = lookup("flag", None)
    .or_else(|| lookup("env", Some(9000)))
    .or_else(|| lookup("file", Some(7000)));
assert_eq!(port, Some(9000));
assert_eq!(*tried.borrow(), ["flag", "env"]);   // the file was never read

2. as_ vs to_ vs into_ -- how much work is being done

This tells you the cost and the ownership story at a glance:

  • as_ -- a cheap borrow. Just a different view of the same thing. No allocation, no cloning. Think: peeking.
  • to_ -- creates something new but leaves the original alone. Usually involves allocation or conversion. Think: photocopying.
  • into_ -- consumes the original and transforms it. The original is gone. Think: metamorphosing.
let s = String::from("hello");

// as_ -- borrows, cheap, returns a reference
let bytes: &[u8] = s.as_bytes();   // &String -> &[u8], no copy
let slice: &str = s.as_str();     // &String -> &str, no copy

// to_ -- copies/converts, original untouched
let upper: String = s.to_uppercase();  // creates a new String
let owned: String = "hi".to_owned();   // &str -> String, allocates

// into_ -- consumes, original is gone
let bytes: Vec<u8> = s.into_bytes(); // String consumed, Vec reuses its buffer
// println!("{s}");                      // ERROR: s has been moved

as_ is O(1) and virtually free. to_ usually allocates. into_ is often more efficient than to_ because it can reuse the existing buffer instead of copying it.

Clarification Which one to use: decide by what happens to the original next

If you're only reading it for now, use as_. If you need an owned value and still need the original, use to_. If you're finished with the original, use into_, which can hand over its buffer instead of copying it. as_ptr shows which ones share memory:

let s = String::from("hello");
let buf = s.as_ptr();

let view: &str = s.as_str();           // as_: the same bytes, nothing copied
assert_eq!(view.as_ptr(), buf);

let copy: String = s.to_owned();       // to_: a new allocation, s untouched
assert_ne!(copy.as_ptr(), buf);
assert_eq!(s, "hello");

let bytes: Vec<u8> = s.into_bytes();   // into_: s is gone, its buffer lives on
assert_eq!(bytes.as_ptr(), buf);
assert_eq!(bytes, b"hello");

The same test works at a function call. If the function takes &str, lend it &s. If it takes a String and you won't use s again, pass s itself. Clone only when you need both.

The pattern repeats across the standard library: 

Path::as_os_str()        // borrow: &Path -> &OsStr
Path::to_path_buf()      // copy:   &Path -> PathBuf
PathBuf::into_os_string() // move:   PathBuf -> OsString

OsStr::as_encoded_bytes() // borrow
OsStr::to_os_string()     // copy
OsString::into_string()   // move

Clarification to_ on small Copy types doesn't allocate

The allocation in to_ comes from building an owned copy of something borrowed, like &str to String. On small Copy types such as char and integers, to_ just returns a new value and nothing touches the heap. And for &str, the usual ways of getting a String all give the same result, so pick the one that reads best.

assert_eq!('a'.to_ascii_uppercase(), 'A');   // char in, char out
assert_eq!('7'.to_digit(10), Some(7));
assert_eq!(258u16.to_be_bytes(), [1, 2]);    // a [u8; 2], on the stack

let a: String = "hi".to_owned();
let b: String = "hi".to_string();
let c: String = String::from("hi");
let d: String = "hi".into();
assert!(a == b && b == c && c == d);

3. _map as a combiner -- two operations in one pass

When a method ends in _map, it performs a transformation as part of another operation. The second word is always map because mapping is the universal glue operation: 

let v = vec![1, 2, 3, 4, 5];

// filter_map = filter + map in one step
// Return Some(value) to keep, None to discard
let evens_doubled: Vec<i32> = v.iter()
    .filter_map(|&x| if x % 2 == 0 { Some(x * 2) } else { None })
    .collect();
// [4, 8]

// find_map = find + map -- find the first match and transform it
let first_even_squared: Option<i32> = v.iter()
    .find_map(|&x| if x % 2 == 0 { Some(x * x) } else { None });
// Some(4)

// flat_map = map + flatten -- map each element to an iterator, then flatten
let words = vec!["hello world", "foo bar"];
let all: Vec<&str> = words.iter()
    .flat_map(|s| s.split_whitespace())
    .collect();
// ["hello", "world", "foo", "bar"]

Clarification filter_map, or filter then map?

Use filter_map when deciding and transforming are the same work, as with parsing: you can't tell a string is a number without parsing it. When the test doesn't depend on the transform, filter and map as two steps read more easily than one closure with an if. find_map follows the same rule for the first match. Count what each item turns into to pick the adapter: exactly one is map, zero or one is filter_map, zero or more is flat_map.

let inputs = ["1", "x", "3"];

// The test is the transform: filter_map parses each item once
let nums: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();
assert_eq!(nums, [1, 3]);

// filter, then map, would parse every valid item twice
let twice: Vec<i32> = inputs.iter()
    .filter(|s| s.parse::<i32>().is_ok())
    .map(|s| s.parse().unwrap())
    .collect();
assert_eq!(twice, nums);

// An independent test: two steps read better than if/else inside filter_map
let v = [1, 2, 3, 4, 5];
let evens_doubled: Vec<i32> = v.iter().filter(|&&x| x % 2 == 0).map(|&x| x * 2).collect();
assert_eq!(evens_doubled, [4, 8]);

// One each, zero or one each, zero or more each
let lines = ["hello world", "", "foo"];
let one: Vec<usize> = lines.iter().map(|l| l.len()).collect();
let first_words: Vec<&str> = lines.iter().filter_map(|l| l.split_whitespace().next()).collect();
let all_words: Vec<&str> = lines.iter().flat_map(|l| l.split_whitespace()).collect();
assert_eq!(one, [11, 0, 3]);
assert_eq!(first_words, ["hello", "foo"]);           // "" has no first word
assert_eq!(all_words, ["hello", "world", "foo"]);    // "hello world" has two

The pattern works on Option and Result too, not just iterators: 

let maybe_str: Option<&str> = Some("42");

// and_then is Option's version of flat_map:
// map would give Option<Option<i32>>; and_then flattens it to Option<i32>
let parsed: Option<i32> = maybe_str.and_then(|s| s.parse().ok());

Clarification map or and_then?

Look at what the closure returns. A plain value goes with map. If the closure returns an Option itself, use and_then; map would wrap it a second time. Result has the same pair, and its and_then needs both steps to share an error type.

let maybe_str: Option<&str> = Some("42");

let a: Option<usize> = maybe_str.map(|s| s.len());                // a plain value: map
let b: Option<Option<i32>> = maybe_str.map(|s| s.parse().ok());   // an Option: map nests it
let c: Option<i32> = maybe_str.and_then(|s| s.parse().ok());      // and_then doesn't
assert_eq!((a, b, c), (Some(2), Some(Some(42)), Some(42)));

let r: Result<&str, String> = Ok("42");
let n: Result<i32, String> = r.and_then(|s| s.parse::<i32>().map_err(|e| e.to_string()));
assert_eq!(n, Ok(42));

4. _while adds a predicate

The base method takes a count. The _while variant takes a condition instead. take takes a count, take_while takes a condition. Same for skip vs skip_while: 

let v = vec![1, 2, 3, 4, 5];

// take(n) -- take exactly n elements
let first_three: Vec<&i32> = v.iter().take(3).collect();
// [1, 2, 3]

// take_while(predicate) -- take while condition holds
let small: Vec<&i32> = v.iter().take_while(|&&x| x < 4).collect();
// [1, 2, 3]

// skip(n) -- skip exactly n elements
let after_two: Vec<&i32> = v.iter().skip(2).collect();
// [3, 4, 5]

// skip_while(predicate) -- skip while condition holds
let from_three: Vec<&i32> = v.iter().skip_while(|&&x| x < 3).collect();
// [3, 4, 5]

The pattern is consistent: the base version works with a fixed count, _while makes it dynamic. Crucially, the condition stops being checked at the first false: take_while ends there, and skip_while lets everything after it through, unchecked.

Clarification take, take_while or filter?

Use take and skip when you know the count up front. Use take_while and skip_while when the boundary is the first item that fails a test: the end of a sorted run, a header block, leading blanks. Use filter when the test applies to every item, wherever it is. On data that isn't sorted, the three come apart:

let v = [1, 2, 7, 3, 9];

assert_eq!(v.iter().take(2).collect::<Vec<_>>(), [&1, &2]);
assert_eq!(v.iter().take_while(|&&x| x < 5).collect::<Vec<_>>(), [&1, &2]);   // stops at 7
assert_eq!(v.iter().filter(|&&x| x < 5).collect::<Vec<_>>(), [&1, &2, &3]);   // finds the 3 as well

// skip_while stops testing at the first false and lets the rest through
assert_eq!(v.iter().skip_while(|&&x| x < 5).collect::<Vec<_>>(), [&7, &3, &9]); // 3 < 5, kept anyway

Clarification Two things to know before you use take_while

First, take_while has to look at the item that fails the test, so that item is used up. If you need it afterwards, use peekable and next_if, or find the boundary with position. Second, when you want to transform items until the first one that doesn't work, map_while does both in one step.

let v = [1, 2, 7, 3, 9];

let mut it = v.iter();
let head: Vec<&i32> = it.by_ref().take_while(|&&x| x < 5).collect();
assert_eq!(head, [&1, &2]);
assert_eq!(it.next(), Some(&3));   // the 7 is gone

// position finds the boundary without using anything up
let cut = v.iter().position(|&x| x >= 5).unwrap_or(v.len());
assert_eq!((&v[..cut], &v[cut..]), (&[1, 2][..], &[7, 3, 9][..]));

// map_while: parse until the first thing that isn't a number
let parsed: Vec<i32> = ["1", "2", "x", "4"].iter().map_while(|s| s.parse().ok()).collect();
assert_eq!(parsed, [1, 2]);

5. _by / _by_key -- "by what measure?"

The base method uses natural ordering (Ord). The _by variant lets you supply a custom comparator. The _by_key variant lets you say "compare by this extracted value": 

let words = vec!["cherry", "fig", "apple", "date"];

// min() -- natural ordering (alphabetical for strings)
let first = words.iter().min();
// Some("apple")

// min_by -- custom comparator
let shortest = words.iter()
    .min_by(|a, b| a.len().cmp(&b.len()));
// Some("fig")

// min_by_key -- compare by extracted key (simpler when you can)
let shortest = words.iter()
    .min_by_key(|w| w.len());
// Some("fig")

The same trio appears for max, sort, and others: 

// Sorting
v.sort();                          // natural order
v.sort_by(|a, b| b.cmp(a));        // custom comparator (here: reverse)
v.sort_by_key(|item| item.score);   // compare by extracted field

// Max
v.iter().max();                     // natural order
v.iter().max_by(|a, b| ...);       // custom comparator
v.iter().max_by_key(|x| ...);      // compare by extracted key

Use _by_key for comparing a single property or derived value. Use _by for complex logic, such as multi-field tie-breaking or custom sort orders.

Clarification _by_key or _by: where the line actually falls

Start with _by_key: it's shorter and names what decides the order. Several fields still fit, as a tuple, and Reverse flips one of them. Switch to _by when the key can't be handed back on its own: a float (f64 isn't Ord, so compare with total_cmp), or a key that borrows from the item. _by also breaks ties with then_with without cloning anything.

use std::cmp::Reverse;

struct Player { name: String, score: u32, time: f64 }
fn names(ps: &[Player]) -> Vec<&str> { ps.iter().map(|p| p.name.as_str()).collect() }

let mut players = vec![
    Player { name: "Bo".into(), score: 90, time: 12.5 },
    Player { name: "Al".into(), score: 90, time: 11.0 },
    Player { name: "Cy".into(), score: 70, time: 9.0 },
];

// Score high to low, then name A to Z: a tuple key (clones each name)...
players.sort_by_key(|p| (Reverse(p.score), p.name.clone()));
assert_eq!(names(&players), ["Al", "Bo", "Cy"]);
// ...or _by with then_with (no clone)
players.sort_by(|a, b| b.score.cmp(&a.score).then_with(|| a.name.cmp(&b.name)));
assert_eq!(names(&players), ["Al", "Bo", "Cy"]);

// A float: _by_key won't compile, total_cmp works
players.sort_by(|a, b| a.time.total_cmp(&b.time));
assert_eq!(names(&players), ["Cy", "Al", "Bo"]);

// A key that borrows from the item: _by_key can't return it, _by compares the borrows
// players.sort_by_key(|p| &p.name);   // error: lifetime may not live long enough
players.sort_by(|a, b| a.name.cmp(&b.name));
assert_eq!(names(&players), ["Al", "Bo", "Cy"]);

Clarification Ties, stability, and a key that's expensive to compute

Three details that decide between close variants. sort and sort_by_key are stable: items that compare equal keep their order, which matters when you sort by one field after another. The sort_unstable versions are often faster when you don't care about that. On ties, max_by_key returns the last of the equals and min_by_key the first. And sort_by_cached_key computes each key at most once, which pays off when the key allocates or does real work; for a plain field, the docs say sort_by_key is likely faster.

use std::cell::Cell;

// Stable: equal keys keep their original order
let mut words = vec!["bb", "a", "cc", "d"];
words.sort_by_key(|w| w.len());
assert_eq!(words, ["a", "d", "bb", "cc"]);   // "a" still before "d", "bb" before "cc"

// Ties in max and min
let words = ["bb", "a", "cc", "d"];
assert_eq!(words.iter().max_by_key(|w| w.len()), Some(&"cc"));   // the last of the longest
assert_eq!(words.iter().min_by_key(|w| w.len()), Some(&"a"));    // the first of the shortest

// An expensive key, computed at most once per item
let calls = Cell::new(0);
let mut names = vec!["bo", "Al", "cy", "Di"];
names.sort_by_cached_key(|n| {
    calls.set(calls.get() + 1);
    n.to_lowercase()
});
assert_eq!(names, ["Al", "bo", "cy", "Di"]);
assert!(calls.get() <= names.len());

6. copied vs cloned -- how expensive is the copy?

Both do the same thing: turn an iterator of references into an iterator of owned values. Same idea (get an owned value from a reference), but copied is for small cheap types and cloned is for anything: 

let v = vec![1, 2, 3];

// copied -- requires T: Copy (small, cheap types: integers, bools, floats)
let owned: Vec<i32> = v.iter().copied().collect();

// cloned -- requires T: Clone (anything, but might be expensive)
let owned: Vec<i32> = v.iter().cloned().collect();

Both work here because integers implement both Copy and Clone. The difference matters for intent and guarantees: 

let strings = vec![String::from("a"), String::from("b")];

// strings.iter().copied()  -- WON'T COMPILE: String isn't Copy
let owned: Vec<String> = strings.iter().cloned().collect(); // works

If it compiles with copied, prefer it. It signals to the reader that the copy is trivial -- a memcpy of a few bytes, not a heap allocation. When you see cloned, you know something more expensive might be happening.

Clarification copied, cloned, into_iter, or nothing at all?

First ask whether you need owned values. If you're only reading, keep the references and copy nothing. If you need owned values and the items are Copy, use copied. If they aren't Copy and you still need the collection, use cloned. If you're done with the collection, into_iter moves the items out and nothing is cloned. copied and cloned work on an Option<&T> too.

let strings = vec![String::from("a"), String::from("b")];
let buf = strings[0].as_ptr();

let found: Option<&String> = strings.iter().find(|s| s.as_str() == "a");   // reading: no copy
assert_eq!(found.map(|s| s.as_ptr()), Some(buf));

let cloned: Vec<String> = strings.iter().cloned().collect();   // new Strings, originals kept
assert_ne!(cloned[0].as_ptr(), buf);
assert_eq!(cloned, strings.to_vec());                          // to_vec() says it shorter

let kept: Vec<String> = strings.into_iter().filter(|s| s.as_str() != "b").collect();
assert_eq!(kept[0].as_ptr(), buf);                             // moved out, not cloned

let v = [10, 20];
assert_eq!(v.first().copied(), Some(10));                      // Option<&i32> to Option<i32>

Putting it all together

These six conventions are composable. You can predict method names you've never seen:

  • ok_or_else -- converts Option to Result, computing the error lazily (_or_else = closure)
  • into_keys -- consumes a HashMap and gives you owned keys (into_ = consuming)
  • max_by_key -- finds the maximum by an extracted value (_by_key = extracted comparison)
  • to_ascii_uppercase -- creates a new value, leaves the original (to_ = new allocation)

When you encounter a new type in the standard library, you can often guess what methods it has. Does it have as_ref? Probably. Does it have into_inner? If it wraps something, yes. Does the iterator adapter have a _by_key variant? Check, but likely.

The naming isn't arbitrary. It's a system. Learn these six meta-patterns and the standard library stops feeling like a phone book and starts feeling like a language you can read.
