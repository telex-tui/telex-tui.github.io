How to read this guide

Every code block marks its angle brackets with a caret line and a circled number, and a table under the block explains each number.

Caret lines

Under a code line, a comment line puts ^ under each marked bracket, from its < to its matching >. The next comment line puts a circled number under the first ^. When one marked bracket sits inside another, as in Vec<Vec<T>>, the inner one gets its own two lines below.

I name a position by the token immediately before the <: "the < immediately after first", "the < immediately after the keyword impl", "the < immediately after ::".

Two tokens contain > but are never brackets, so I never mark them: -> (the arrow before a return type) and => (the arrow in a match arm). A < or > that is a comparison operator is marked and labelled "other: comparison operator". Item 18 covers operators.

Labels

Every marked bracket gets one of three labels:

  • DECLARE: the <…> introduces new names (type, lifetime or const parameters).
  • SUPPLY: the <…> fills declared parameters with generic arguments: specific types, lifetimes or constants, or parameters passed on from a DECLARE list (see "The Arguments column" below).
  • other: anything else. I name what it is.

Terms

Each term below is defined once, against this program, and used with exactly this meaning everywhere after.

Lifetimes are the one place where "concrete" has no direct equivalent. The borrow checker fills a lifetime parameter with a region of code, and regions have no names you can write, except 'static. So where other examples show a concrete type, lifetime examples show a placeholder and say which code determines the region.

Telling same-named parameters apart

Many examples declare several parameters all named T. I tell them apart by the DECLARE list that declared each one. "T from impl<T>" means the T declared in the < immediately after the keyword impl; "T from struct Wrapper<T>" means the T declared in the < immediately after Wrapper in the struct definition. Two parameters with the same name in different DECLARE lists are unrelated.

The Arguments column

Every table that explains numbered marks has an Arguments column, filled in for SUPPLY rows. A SUPPLY list fills another item's parameters, but what it fills them with isn't always a finished type yet. Ordinary function arguments work the same way:

Compiles.

fn double(n: i32) -> i32 {
    n * 2
}

fn quadruple(x: i32) -> i32 {
    double(double(x))
}

fn main() {
    println!("{}", quadruple(4));
}

Output:

16

Inside quadruple, x isn't a number yet. The inner double(x) doesn't hand over a value; it passes on whatever the caller gives quadruple. Only quadruple(4) in main supplies an actual value, and that 4 flows through x into double's n.

The mental model: blanks, and who fills them

Every <…> either creates blanks (a DECLARE list) or fills blanks (a SUPPLY list). For every blank, three questions tell you everything: where its name can be used (its scope), who fills it, and when. Items 1–4 are four places a DECLARE list can sit, and each one has a different answer to "who fills it".

This program has one DECLARE list in each of those four places.

Four rules that follow from the model

Each rule names the item where its example compiles and fails in full.

  1. A DECLARE list tells the compiler which names are new. Without one, T is looked up as an existing type. Write this: impl<T> Wrapper<T> { … }. Not this: impl Wrapper<T> { … }, which fails with E0425, "cannot find type T in this scope" (item 4).
  2. A generic body is checked once, against its bounds, not once per instantiation. The body may use only what the bounds promise, even if every actual caller passes a type that could do more. Write this when the body uses >: fn largest<T: Ord + Copy>(items: &[T]) -> T. Not this: fn largest<T: Copy>(items: &[T]) -> T, which fails with E0369 even though the only call passes i32 (item 1).
  3. Each instantiation is a separate type or a separate function. Pair<u8> and Pair<u32> are unrelated types. To turn a Pair<u8> into a Pair<u32>, write this: let big: Pair<u32> = Pair { left: u32::from(small.left), right: u32::from(small.right) };. Not this: let big: Pair<u32> = small;, which fails with E0308 (item 2).
  4. Every blank must be filled before code is generated. If no SUPPLY list, no inference and no matching fills it, compilation stops. Write this: let name: String = make();. Not this: let thing = make();, which fails with E0283, "type annotations needed" (item 1).

Item 1 — Function items: fn name<…>(…)

A DECLARE list immediately after a function's name declares generic parameters that the caller fills at each call site, either with a turbofish or through inference.

The DECLARE list sits between the function's name and its function parameter list, which is the (…) of ordinary parameters, such as (_value: T) below. "Generic parameter" always means a name in <…>; "function parameter" always means a name in (…).

5.2 When T becomes concrete in each version

Design guide: where to write <T> in a trait

Pick the shape by asking two questions about the code that must work: who decides the type, and how many types each implementing type needs. Five rules cover the cases. Each shows "write this" and "not this", both compile-checked.

The three shapes:

  • (a) <T> immediately after the trait's name: trait Processor<T> { fn process(&self, input: T); }
  • (b) <T> immediately after the method's name: trait Processor { fn process<T>(&self, input: T); }
  • (c) no <T> at all, an associated type in the trait body: trait Processor { type Input; fn process(&self, input: Self::Input); }. Each impl sets it once, with a line such as type Input = i32;, and code refers to it as Self::Input or P::Input. Rule 3 compiles one.

Write this. Compiles. The (c) form; the (a) form, &dyn Processor<i32>, compiles in 5.6.

struct Logger;

Rule 5: the caller picks the input type, and the impl fixes the output type → (a) for the input, (c) for the output
