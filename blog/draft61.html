40 Rust Patterns That Matter

November 2026

You can read the Rust standard library docs cover-to-cover and still not know how to think in Rust. The docs tell you what each method does. They don't tell you when you'd reach for it, or which three methods combine to solve the problem you're actually staring at.

This is a field guide to forty patterns that show up constantly in real Rust code. Each one is a small decision -- a moment where you know what you want but don't know the idiomatic way to say it. They're grouped by the kind of problem they solve, not by which trait they live on.

This version adds a clarification box under each pattern. Patterns often mention something in passing -- what as_ref hands back, the & in |&p|, what {:4} means -- and the box stops to pin it down in code. The boxes are mostly assert lines, so the expected output is part of the code: paste any box into a #[test] function and it passes. A let _: T = ... line is a type check: it only compiles if the value really is a T.

I. Errors and Options

These patterns are about control flow. Rust doesn't have exceptions, so Result and Option are your control flow. The patterns here are the grammar for saying "this might fail" and "here's what to do about it."

1. The Success or Bail

You have a list of tasks. If they all succeed, you want the collected results. If any one fails, the whole batch is a failure.

The trick is that collect() knows how to do this. When you collect an iterator of Result<T, E> into a Result<Vec<T>, E>, Rust short-circuits on the first error and gives you back that error. If everything succeeds, you get Ok(vec_of_results). 

let results: Result<Vec<i32>, _> = items.iter().map(|&x| x.try_into()).collect();
// [Ok(1), Ok(2), Ok(3)] -> Ok([1, 2, 3])
// [Ok(1), Err(e), Ok(3)] -> Err(e)

This replaces the loop-with-early-return pattern you'd write in C. The FromIterator implementation for Result handles the bail-out logic internally.

Clarification collect stops at the first Err

The short-circuit is real: once collect sees an Err, it stops pulling, so the rest of the chain never runs on the later items. The same FromIterator trick works for Option, and sum and product work the same way.

let parsed: Result<Vec<i32>, _> = ["1", "2", "3"].iter().map(|s| s.parse::<i32>()).collect();
assert_eq!(parsed, Ok(vec![1, 2, 3]));

let mut pulled = Vec::new();
let parsed: Result<Vec<i32>, _> = ["1", "x", "3"]
    .iter()
    .inspect(|s| pulled.push(**s))
    .map(|s| s.parse::<i32>())
    .collect();
assert!(parsed.is_err());
assert_eq!(pulled, ["1", "x"]);   // "3" was never pulled

// Option works the same way: the first None wins
let all: Option<Vec<i32>> = [Some(1), None, Some(3)].into_iter().collect();
assert_eq!(all, None);

// and so does sum
let total: Result<i32, String> = [Ok(1), Ok(2), Ok(3)].into_iter().sum();
assert_eq!(total, Ok(6));

2. The Error Pivot

You're inside a function that returns Result, but you have an Option. You need to turn "nothing here" into a specific error so you can use ? to propagate it. 

let val = maybe_user.ok_or(Error::NotFound)?;
// Some(user) -> Ok(user)
// None       -> Err(NotFound)

ok_or bridges the two types: Some(x) becomes Ok(x), and None becomes Err(whatever_you_passed). If constructing the error is expensive, use ok_or_else with a closure so it only runs on the None path. 

// This builds the error string even when maybe_user is Some:
let val = maybe_user.ok_or(format!("User {} not found", id))?;

// This only builds it when needed:
let val = maybe_user.ok_or_else(|| format!("User {} not found", id))?;

Clarification What ? does with the error

On a Result, ? is a match that returns early on Err, and on the way out it converts the error with From. That's how ok_or with a plain &str can feed a function that returns Result<_, String>.

fn first_char(s: &str) -> Result<char, String> {
    let c = s.chars().next().ok_or("empty input")?;   // &str becomes String via From
    Ok(c)
}
assert_eq!(first_char("hi"), Ok('h'));
assert_eq!(first_char(""), Err(String::from("empty input")));

// The ? line, written out by hand
fn first_char_longhand(s: &str) -> Result<char, String> {
    let c = match s.chars().next().ok_or("empty input") {
        Ok(c) => c,
        Err(e) => return Err(From::from(e)),
    };
    Ok(c)
}
assert_eq!(first_char_longhand(""), first_char(""));

// ? won't turn an Option into a Result for you; that's ok_or's job:
// fn first(s: &str) -> Result<char, String> { Ok(s.chars().next()?) }
// error[E0277]: the `?` operator can only be used on `Result`s, not `Option`s,
//               in a function that returns `Result`

3. The Silent Discard

You have a list of inputs and some of them are garbage. You want to keep the good ones and pretend the bad ones never existed. No error handling, no logging -- just drop them on the floor.

Map the fallible operation to an Option with .ok(), then use filter_map to keep only the Some values. 

let valid: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();
// ["1", "abc", "3"] -> [1, 3]

The .ok() call converts Result<T, E> into Option<T>, discarding the error. Then filter_map does a filter-and-unwrap in one step: keep the Somes, skip the Nones.

Clarification Option is a collection of zero or one

An Option behaves like a collection holding at most one item, so filter_map(f) does the same job as flat_map(f), which flattens whatever collections f returns. Result works the same way: Ok holds one item and Err holds none. So these three lines agree:

let inputs = ["1", "abc", "3"];

let a: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();
let b: Vec<i32> = inputs.iter().map(|s| s.parse().ok()).flatten().collect();
let c: Vec<i32> = inputs.iter().flat_map(|s| s.parse()).collect();   // no .ok() at all
assert_eq!(a, [1, 3]);
assert_eq!(a, b);
assert_eq!(a, c);

// The pieces
assert_eq!("7".parse::<i32>().ok(), Some(7));
assert_eq!("x".parse::<i32>().ok(), None);
assert_eq!(Some(7).into_iter().count(), 1);
assert_eq!(None::<i32>.into_iter().count(), 0);

4. The Specific Failure Context

An operation failed, but the error is too generic. "File not found" isn't helpful when you know which file and why you were reading it. You want to wrap the error in something more specific without losing the original. 

let config = load_file(path)
    .map_err(|e| AppError::ConfigLoad { path: path.into(), source: e })?;
// Ok(cfg)        -> Ok(cfg)
// Err(io_error)  -> Err(AppError::ConfigLoad { path, source: io_error })

map_err transforms only the error side and leaves Ok values completely untouched. It's the error equivalent of map, which transforms only the success side.

Clarification The original error is still in there

Wrapping doesn't lose the original error. If the wrapper returns it from Error::source, the message stays specific and the cause stays reachable. (With thiserror, a field named source gets this for free.)

use std::error::Error;
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
struct ConfigLoad { path: String, source: ParseIntError }

impl fmt::Display for ConfigLoad {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "could not load {}", self.path)
    }
}

impl Error for ConfigLoad {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        Some(&self.source)
    }
}

let err = "80x".parse::<u16>()
    .map_err(|e| ConfigLoad { path: "app.toml".into(), source: e })
    .unwrap_err();

assert_eq!(err.to_string(), "could not load app.toml");                     // the context
assert_eq!(err.source().unwrap().to_string(), "invalid digit found in string"); // the cause

5. The Fallback Chain

You have multiple places a value might come from. Try the first; if it's None, try the second; if that's None, try the third. 

let color = user_preference
    .or(theme_default)
    .or(Some(Color::Black));
// Some(Red).or(Some(Blue)).or(Some(Black)) -> Some(Red)
// None.or(None).or(Some(Black))            -> Some(Black)

or on Option returns the first Some it finds. The same pattern works on Result -- the first Ok wins. If computing the fallback is expensive, use or_else with a closure: 

let config = load_from_file()
    .or_else(|_| load_from_env())
    .or_else(|_| load_defaults());

This is a try-one-then-try-another chain, and it reads exactly like one.

Clarification When every fallback fails, you get the last error

On Result, or keeps the first Ok and drops the errors along the way, so a chain that fails all the way down reports only the last one. or_else hands each error to the next attempt, so you can keep it if you want.

assert_eq!(Some(1).or(Some(2)), Some(1));
assert_eq!(None.or(Some(2)), Some(2));
assert_eq!(None::<i32>.or(None), None);

let from_file: Result<u16, &str> = Err("no file");
let from_env: Result<u16, &str> = Err("no env var");
assert_eq!(from_file.or(from_env), Err("no env var"));   // "no file" is gone

fn read_env() -> Result<u16, String> { Err(String::from("no env var")) }
let r: Result<u16, String> = Err(String::from("no file"))
    .or_else(|e| read_env().map_err(|e2| format!("{e}; {e2}")));   // or keep both
assert_eq!(r, Err(String::from("no file; no env var")));

// The rest of the family
assert_eq!(Some(1).and(Some(2)), Some(2));   // both must be Some; you get the second
assert_eq!(Some(1).xor(Some(2)), None);      // exactly one must be Some
assert_eq!(Some(1).xor(None), Some(1));

6. The Safe Default

A value might be missing, and you're fine with the type's default (0 for numbers, "" for strings, [] for vecs). You don't want to spell out what the default is because the type already knows. 

let count = maybe_count.unwrap_or_default(); // None -> 0 for integers
let name = maybe_name.unwrap_or_default();   // None -> "" for String

This requires that T implements Default. It's a small thing, but it eliminates a class of "what should the default be?" decisions and makes the intent crystal clear: "I want the zero value."

Clarification What Default gives you

Each type decides what its default is. #[derive(Default)] builds a struct's default field by field, and an enum picks its default variant with #[default].

assert_eq!(i32::default(), 0);
assert_eq!(f64::default(), 0.0);
assert_eq!(bool::default(), false);
assert_eq!(char::default(), '\0');
assert_eq!(String::default(), "");
assert!(Vec::<u8>::default().is_empty());
assert_eq!(Option::<u8>::default(), None);
assert_eq!(<(u8, bool)>::default(), (0, false));

#[derive(Default, Debug, PartialEq)]
struct Settings { retries: u32, verbose: bool, name: String }
assert_eq!(Settings::default(), Settings { retries: 0, verbose: false, name: String::new() });

#[derive(Default, Debug, PartialEq)]
enum Level { Debug, #[default] Info, Warn }
assert_eq!(Level::default(), Level::Info);

let missing: Option<Settings> = None;
assert_eq!(missing.unwrap_or_default().retries, 0);

7. The Nested Collapse

You end up with an Option<Option<T>> -- usually because you mapped over an Option with a function that itself returns an Option. You want to flatten it down to a single Option<T>. 

let nested: Option<Option<i32>> = Some(Some(42));
let flat: Option<i32> = nested.flatten(); // Some(42)

let also_nested: Option<Option<i32>> = Some(None);
let also_flat: Option<i32> = also_nested.flatten(); // None

This comes up more than you'd expect. Any time you call .map(|x| something_that_returns_option(x)) you get the double wrapping. You can either switch to and_then (pattern 33 below) to avoid it in the first place, or flatten to clean it up after.

Clarification map + flatten = and_then

The double wrapping comes from mapping with a function that already returns an Option. flatten peels off one layer afterwards; and_then never adds it.

fn half(n: i32) -> Option<i32> {
    if n % 2 == 0 { Some(n / 2) } else { None }
}

assert_eq!(Some(8).map(half), Some(Some(4)));    // Option<Option<i32>>
assert_eq!(Some(8).map(half).flatten(), Some(4));
assert_eq!(Some(8).and_then(half), Some(4));     // the same, in one step
assert_eq!(Some(7).and_then(half), None);        // half said no
assert_eq!(None.and_then(half), None);           // half never ran

// flatten removes one layer at a time
let deep: Option<Option<Option<i32>>> = Some(Some(Some(1)));
assert_eq!(deep.flatten(), Some(Some(1)));
assert_eq!(deep.flatten().flatten(), Some(1));

// Result has both too (Result::flatten since Rust 1.89)
let nested: Result<Result<i32, String>, String> = Ok(Ok(1));
assert_eq!(nested.clone().flatten(), Ok(1));
assert_eq!(nested.and_then(|inner| inner), Ok(1));

8. The Conditional Keep

You have an Option and you want to keep it only if the inner value passes a test. If it fails the test, turn the whole thing into None. 

let port: Option<u16> = Some(8080);
let valid_port = port.filter(|&p| p > 1024);  // Some(8080)
let low_port = Some(80_u16).filter(|&p| p > 1024); // None

filter on Option is the gatekeeper. It either lets the Some through or downgrades it to None. Useful for validation chains where you want to keep everything in Option-land without unwrapping.

Clarification The & in |&p|

Option::filter passes the closure a &u16, so it can look at the value without taking it. Closure parameters are patterns, and &p matches the reference and binds the u16 inside. These three closures run the same test:

let port = Some(8080_u16);

assert_eq!(port.filter(|&p| p > 1024), Some(8080));   // the pattern strips the &
assert_eq!(port.filter(|p| *p > 1024), Some(8080));   // deref by hand
assert_eq!(port.filter(|p| p > &1024), Some(8080));   // compare &u16 with &u16

// A reference and a plain number don't compare:
// port.filter(|p| p > 1024)
// error[E0308]: mismatched types
//               expected `&u16`, found integer

// &p copies the value out of the reference, so it only works for Copy types.
// For a String, keep the reference:
let name = Some(String::from("Al"));
assert_eq!(name.filter(|s| s.len() > 1).as_deref(), Some("Al"));

9. The Borrow, Don't Move

You have an Option<String> and you want to peek at the contents without taking ownership. You want Option<&String> or Option<&str>. 

let name: Option<String> = Some("Alice".to_string());

// as_ref: Option<String> -> Option<&String>
if name.as_ref().is_some_and(|s| s.starts_with('A')) {
    // name is still usable here
}

// as_deref: Option<String> -> Option<&str> (even better)
match name.as_deref() {
    Some("Alice") => println!("Found Alice"),
    Some(other) => println!("Found {other}"),
    None => println!("Nobody home"),
}

as_ref gives you a reference to whatever's inside. as_deref goes one step further and dereferences it too, so Option<String> becomes Option<&str>. The same pair works on Result: as_ref gives you Result<&T, &E>.

Clarification as_ref and as_deref, in asserts

as_ref takes &Option<String> and gives you a new Option<&String> that you can consume freely, leaving the original alone. as_deref also derefs what's inside, which is why it can be compared with a string literal.

let name: Option<String> = Some(String::from("Alice"));

let _: Option<&String> = name.as_ref();   // borrows the String inside
let _: Option<&str> = name.as_deref();    // ...and derefs it to str

assert_eq!(name.as_ref().map(|s| s.len()), Some(5));
assert_eq!(name.as_ref(), Some(&String::from("Alice")));   // as_ref compares with a &String
assert_eq!(name.as_deref(), Some("Alice"));                // as_deref with a literal
assert!(name.is_some());                                   // name still owns its String

// Without as_ref, map takes the String out of name:
// let len = name.map(|s| s.len());
// println!("{name:?}");   // error[E0382]: borrow of moved value: `name`

// as_mut is the same idea with a mutable borrow
let mut name = name;
if let Some(s) = name.as_mut() {
    s.push('!');
}
assert_eq!(name.as_deref(), Some("Alice!"));

// On Result, as_deref derefs only the Ok side
let res: Result<String, String> = Err(String::from("boom"));
let _: Result<&str, &String> = res.as_deref();
assert_eq!(res.as_ref().unwrap_err(), "boom");

Despite the name, Option::as_ref is a method of Option, not the AsRef trait you see in bounds like P: AsRef<Path>.

More on this: AsRef, Borrow, and ToOwned

10. The Map the Wrapper

You have a Result or Option and want to transform what's inside without unwrapping it. This is the bread-and-butter combinator. 

let maybe_len: Option<usize> = maybe_name.map(|s| s.len());
// Some("Alice") -> Some(5)
// None          -> None
let parsed: Result<i32, _> = line.map(|s| s.trim().len() as i32);
// Ok(" hello ") -> Ok(5)
// Err(e)        -> Err(e)

map on Option transforms Some(x) to Some(f(x)) and leaves None alone. map on Result transforms Ok(x) to Ok(f(x)) and leaves Err alone. It's how you work with wrapped values without leaving the wrapper.

Clarification The closure only runs on Some and Ok

On None or Err, map skips the closure entirely. A function name works in place of a closure, and map_or maps and supplies a fallback in one step.

let some: Option<&str> = Some("Alice");
let none: Option<&str> = None;

assert_eq!(some.map(str::len), Some(5));   // a function name works as the closure
assert_eq!(none.map(str::len), None);
assert_eq!(none.map(|_| -> usize { panic!("never runs") }), None);

// map_or: map, with a value to use for None
assert_eq!(some.map_or(0, str::len), 5);
assert_eq!(none.map_or(0, str::len), 0);

// On Result, map touches only Ok, and map_err only Err
let ok: Result<i32, String> = Ok(2);
let err: Result<i32, String> = Err(String::from("bad"));
assert_eq!(ok.clone().map(|n| n * 10), Ok(20));
assert_eq!(err.clone().map(|n| n * 10), Err(String::from("bad")));
assert_eq!(ok.map_err(|e| e.len()), Ok(2));
assert_eq!(err.map_err(|e| e.len()), Err(3));

II. Ownership and Memory

These patterns are about efficiency -- knowing when you're copying data, when you're borrowing it, and when you're consuming it. In C, you'd manage this with conventions and discipline. In Rust, the patterns have names.

11. The Cheap Reference Upgrade

You have an iterator yielding references to small, Copy types like &i32 or &bool, but the next function in the chain expects owned values. 

let sum: i32 = numbers.iter().copied().sum();
// [1, 2, 3].iter() -> &1, &2, &3 -> .copied() -> 1, 2, 3 -> .sum() -> 6
let flags: Vec<bool> = bits.iter().copied().collect();
// [true, false].iter() -> &true, &false -> .copied() -> true, false

copied() turns &T into T for any type that implements Copy. It's a memcpy of a few bytes -- trivially cheap. When you see copied() in code, you know nothing expensive is happening.

Clarification Which types are Copy?

copied() only compiles for Copy types: plain values with no heap memory or other resource to look after. A function with a T: Copy bound turns the question into a compile-time check.

fn is_copy<T: Copy>() {}

is_copy::<i32>();
is_copy::<bool>();
is_copy::<char>();
is_copy::<&str>();         // shared references are Copy
is_copy::<(u8, f64)>();    // so are tuples and arrays of Copy types
is_copy::<[u16; 4]>();
// is_copy::<String>();    // error[E0277]: the trait bound `String: Copy` is not satisfied
// is_copy::<Vec<i32>>();  // the same: it owns heap memory
// is_copy::<&mut i32>();  // the same: only one &mut can exist at a time

// For Copy items, these all do the same thing
let numbers = [1, 2, 3];
let a: i32 = numbers.iter().copied().sum();
let b: i32 = numbers.iter().map(|&n| n).sum();
let c: i32 = numbers.iter().sum();         // Sum is also implemented for &i32
assert_eq!((a, b, c), (6, 6, 6));

12. The Expensive Reference Upgrade

Same situation, but the types involve heap allocations. You have &String or &Vec<T> and you need owned versions. You accept the cost. 

let owned_names: Vec<String> = name_refs.iter().cloned().collect();
// [&"Alice", &"Bob"] -> ["Alice".clone(), "Bob".clone()] -> heap allocations

cloned() calls .clone() on each element. It compiles for anything that implements Clone, but unlike copied(), it might allocate. When you see cloned() in a review, it's a signal: "heap allocations happening here, and the author knows it."

Clarification Seeing the allocation

A String is a pointer to a heap buffer plus a length and a capacity. clone allocates a new buffer and copies the bytes into it; copying a &str copies only the pointer. as_ptr shows which is which:

let original = String::from("Alice");
let cloned = original.clone();
assert_eq!(original, cloned);                     // same contents...
assert_ne!(original.as_ptr(), cloned.as_ptr());   // ...in a different heap buffer

let r1: &str = &original;
let r2 = r1;                                      // copying a reference
assert_eq!(r2.as_ptr(), original.as_ptr());       // same buffer, nothing allocated

// cloned() makes one of those copies per item
let names = vec![String::from("Alice"), String::from("Bob")];
let owned: Vec<String> = names.iter().cloned().collect();
assert_eq!(owned, names);
assert_ne!(owned[0].as_ptr(), names[0].as_ptr());

13. The Resource Recycle

You're done with a container -- a HashMap, a Vec, a BTreeSet -- but you need the individual items as owned values. You want to tear the container apart. 

for (key, value) in map.into_iter() {
    // key and value are owned -- map is consumed
    other_map.insert(key, value);
}

into_iter() consumes the collection and yields owned items. Compare: .iter() borrows and yields references, .iter_mut() borrows mutably. The into_ prefix follows the standard convention -- it eats the original.

Clarification What a for loop calls

for x in c calls c.into_iter(), and what that yields depends on what c is: the collection itself, a & to it, or a &mut to it.

let mut v = vec![String::from("a"), String::from("b")];

for s in &v {            // the same as v.iter()
    let _: &String = s;
}
for s in &mut v {        // the same as v.iter_mut()
    s.push('!');
}
assert_eq!(v, ["a!", "b!"]);

for s in v {             // the same as v.into_iter(): v moves into the loop
    let _: String = s;
}
// v.len();              // error[E0382]: borrow of moved value: `v`

// Maps too: into_iter yields owned (key, value) pairs
use std::collections::HashMap;
let map = HashMap::from([("k", 1)]);
let pairs: Vec<(&str, i32)> = map.into_iter().collect();
assert_eq!(pairs, [("k", 1)]);

14. The Peeking into the Box

You have a String inside an Option and you want to call string methods on it -- check the length, see if it starts with something -- without moving it out. 

// as_deref: Option<String> -> Option<&str>
let is_empty = maybe_name.as_deref().map_or(true, |s| s.is_empty());

let starts_with_a = maybe_name.as_deref()
    .is_some_and(|s| s.starts_with('A'));

as_deref() uses Deref to give you a borrowed view: Option<String> becomes Option<&str>, Option<Vec<T>> becomes Option<&[T]>, Option<Box<T>> becomes Option<&T>. You get to peek without taking anything out.

Clarification What as_deref derefs to

as_deref is as_ref followed by Deref::deref on the value inside, so you get whatever the inner type derefs to. And the map_or(true, ...) above has a name since Rust 1.82: is_none_or. Clippy suggests it.

let name: Option<String> = Some(String::from("Ann"));
let list: Option<Vec<i32>> = Some(vec![1, 2]);
let boxed: Option<Box<u8>> = Some(Box::new(7));

let _: Option<&str> = name.as_deref();     // String derefs to str
let _: Option<&[i32]> = list.as_deref();   // Vec<T> to [T]
let _: Option<&u8> = boxed.as_deref();     // Box<T> to T

assert_eq!(list.as_deref(), Some(&[1, 2][..]));
assert_eq!(boxed.as_deref(), Some(&7));

// map_or(true, f) and is_none_or(f) say the same thing
assert_eq!(name.as_deref().map_or(true, |s| s.is_empty()), false);
assert_eq!(name.as_deref().is_none_or(|s| s.is_empty()), false);
assert_eq!(None::<&str>.is_none_or(|s| s.is_empty()), true);   // None counts as yes

More on this: Deref Coercion

15. The Temporary Theft

You have an Option inside a mutable struct and you need to take the value out, leaving None behind. You're not borrowing -- you're stealing, but you're leaving the struct in a valid state. 

struct Connection {
    pending_message: Option<Message>,
}

impl Connection {
    fn flush(&mut self) -> Option<Message> {
        self.pending_message.take() // Returns the Message, leaves None
    }
}

Option::take() swaps the contents with None and gives you what was there. It's the clean way to move a value out of a mutable reference without unsafe. You'll see this constantly in state machines, buffered I/O, and event systems.

Clarification Why not just move it out?

Through &mut self you can change a field but not move out of it, because that would leave a hole in a struct that someone else still owns. take moves the value out and puts None in its place in one step. Option has a few more methods that work in place:

// fn flush(&mut self) -> Option<Message> {
//     self.pending_message   // error[E0507]: cannot move out of `self.pending_message`
// }                          //               which is behind a mutable reference

let mut slot: Option<u32> = Some(5);

assert_eq!(slot.take(), Some(5));          // out comes the value...
assert_eq!(slot, None);                    // ...and None stays behind
assert_eq!(slot.take(), None);             // taking from None is fine

assert_eq!(slot.replace(7), None);         // put 7 in, get the old value back
assert_eq!(slot, Some(7));

assert_eq!(slot.take_if(|v| *v > 10), None);     // Rust 1.80: take it only if...
assert_eq!(slot.take_if(|v| *v == 7), Some(7));
assert_eq!(slot, None);

assert_eq!(*slot.get_or_insert(42), 42);   // fill it if it's empty
assert_eq!(slot, Some(42));

16. The Hot Swap

You need to replace a value but also need the old one back. You can't just assign because you need both the old and new values. 

use std::mem;

let mut current = State::Running;
let previous = mem::replace(&mut current, State::Paused);
// current is now Paused, previous is Running

mem::replace puts a new value in and hands you the old one. It's how you do atomic-feeling swaps without Clone and without leaving the variable in an undefined state. Useful any time you need to transition state and react to what the state was.

Clarification replace, swap and take

std::mem has three ways to get a value out from behind a &mut without leaving a hole. None of them clone: they move the bytes.

use std::mem;

let mut state = String::from("running");
let old = mem::replace(&mut state, String::from("paused"));   // put in, get the old one
assert_eq!((old.as_str(), state.as_str()), ("running", "paused"));

let mut a = 1;
let mut b = 2;
mem::swap(&mut a, &mut b);                                    // exchange two places
assert_eq!((a, b), (2, 1));

let mut log = vec!["start", "stop"];
let taken = mem::take(&mut log);                              // leave Default::default()
assert_eq!(taken, ["start", "stop"]);
assert!(log.is_empty());

// Option::take is mem::take, because None is Option's default
let mut slot = Some(3);
assert_eq!(mem::take(&mut slot), Some(3));
assert_eq!(slot, None);

17. The Drain and Keep

You need to remove some elements from a Vec, but you want both the removed elements and the remaining vec -- and you don't want to clone anything. 

let mut items = vec![1, 2, 3, 4, 5];

// drain a range: removes and yields elements 1..3
let removed: Vec<i32> = items.drain(1..3).collect();
// removed = [2, 3], items = [1, 4, 5]

// drain all: empties the vec but keeps the allocation
let all: Vec<i32> = items.drain(..).collect();
// all = [1, 4, 5], items = [] (but buffer is still allocated)

drain is the surgical removal tool. It removes a range in-place, yields the removed elements as an iterator, and shifts remaining elements to fill the gap. The vec's heap allocation is preserved, which matters when you're draining and refilling in a loop.

Clarification Reading range syntax

drain takes the same ranges as slicing: the start is included and the end isn't, unless you write ..=.

let v = [10, 20, 30, 40, 50];

assert_eq!(v[1..3], [20, 30]);         // indices 1 and 2: the end is excluded
assert_eq!(v[1..=3], [20, 30, 40]);    // ..= includes the end
assert_eq!(v[..2], [10, 20]);          // from the start
assert_eq!(v[3..], [40, 50]);          // to the end
assert_eq!(v[..], v);                  // everything
assert_eq!((1..3).len(), 2);           // a range holds end - start items
assert!((1..3).contains(&2));
assert!(!(1..3).contains(&3));

let mut items = vec![1, 2, 3, 4, 5];
let removed: Vec<i32> = items.drain(1..=2).collect();
assert_eq!(removed, [2, 3]);
assert_eq!(items, [1, 4, 5]);

// Dropping a Drain unread still removes the range, and the Vec keeps its buffer
let capacity = items.capacity();
items.drain(..);
assert!(items.is_empty());
assert_eq!(items.capacity(), capacity);

18. The Cow Dance

You have a function that sometimes needs to modify a string and sometimes doesn't. You don't want to clone every time "just in case." 

use std::borrow::Cow;

fn normalize(input: &str) -> Cow<'_, str> {
    if input.contains('\t') {
        Cow::Owned(input.replace('\t', "    "))
    } else {
        Cow::Borrowed(input) // No allocation needed
    }
}
// normalize("hello")     -> Cow::Borrowed("hello")       -- zero-cost
// normalize("he\tllo")   -> Cow::Owned("he    llo")       -- allocates

Cow -- "clone on write" -- is either a reference or an owned value. It lets you defer the allocation decision. When most inputs don't need modification, this avoids the heap allocation entirely. You'll see it in parsers, config processors, and anywhere strings are conditionally transformed.

Clarification Borrowed or owned, it reads the same

A Cow<str> derefs to str either way, so the caller doesn't need to care which it got. to_mut clones only if it's still borrowed, and into_owned gives you a String either way. (The '_ says the result may borrow from input; recent compilers warn if you leave it out.)

use std::borrow::Cow;

fn normalize(input: &str) -> Cow<'_, str> {
    if input.contains('\t') {
        Cow::Owned(input.replace('\t', "    "))
    } else {
        Cow::Borrowed(input)
    }
}

let clean = normalize("hello");
let fixed = normalize("he\tllo");
assert!(matches!(clean, Cow::Borrowed(_)));   // no allocation
assert!(matches!(fixed, Cow::Owned(_)));      // one allocation
assert_eq!(clean, "hello");                   // both compare like strings
assert_eq!(fixed, "he    llo");
assert_eq!(fixed.len(), 9);                   // and have str's methods

let mut c = normalize("abc");
c.to_mut().push('!');                         // Borrowed becomes Owned here
assert!(matches!(c, Cow::Owned(_)));
assert_eq!(c, "abc!");

let s: String = clean.into_owned();           // allocates now, since it was borrowed
assert_eq!(s, "hello");

III. Iterators

Iterators are Rust's data processing pipeline. These patterns are the individual pipe fittings -- each one solves a specific "I have this, I want that" transformation.

19. The Search and Transform

You want to find the first item in a collection that matches some condition, and then immediately extract or transform a value from it. 

let first_admin_email = users.iter()
    .find_map(|u| if u.is_admin { Some(&u.email) } else { None });
// [{admin: false}, {admin: true, email: "a@b.com"}, ...] -> Some("a@b.com")

find_map combines find and map into one pass. Your closure returns Some(value) to say "found it, and here's what I want from it" or None to say "keep looking." It short-circuits on the first Some.

Clarification bool::then_some instead of if ... { Some } else { None }

The closure above turns a bool into an Option. bool has two methods for exactly that: then_some(value), and then(|| value), which only builds the value when the bool is true.

assert_eq!(true.then_some(5), Some(5));
assert_eq!(false.then_some(5), None);
assert_eq!(true.then(|| String::from("built")), Some(String::from("built")));
assert_eq!(false.then(|| String::from("built")), None);   // the closure never ran

struct User { is_admin: bool, email: &'static str }
let users = [
    User { is_admin: false, email: "x@y.com" },
    User { is_admin: true,  email: "a@b.com" },
];

let first_admin = users.iter().find_map(|u| u.is_admin.then_some(u.email));
assert_eq!(first_admin, Some("a@b.com"));

// find, then map: two steps, same answer
let same = users.iter().find(|u| u.is_admin).map(|u| u.email);
assert_eq!(first_admin, same);

20. The Dynamic Boundary

You're processing a stream of data and you need to stop the moment a condition is no longer true. Not "skip the ones that fail" -- stop entirely. 

// Read header lines until the first blank line
let headers: Vec<_> = lines.iter()
    .take_while(|l| !l.is_empty())
    .collect();
// ["Host: x", "Accept: y", "", "body"] -> ["Host: x", "Accept: y"]

take_while is a fence, not a filter. Once the predicate returns false, the iterator is done -- even if later elements would pass. This is what you want for things with structure: headers before a blank line, sorted runs, leading whitespace.

Clarification A fence, not a filter, in asserts

Same data, same test, three adapters. And one more detail: take_while has to look at the first failing item to know it should stop, so that item is used up.

let v = [1, 2, 5, 1, 2];
let small = |n: &&i32| **n < 3;

assert_eq!(v.iter().take_while(small).collect::<Vec<_>>(), [&1, &2]);       // stops at 5
assert_eq!(v.iter().filter(small).collect::<Vec<_>>(), [&1, &2, &1, &2]);   // tests every item
assert_eq!(v.iter().skip_while(small).collect::<Vec<_>>(), [&5, &1, &2]);   // the other half

let mut it = v.iter();
let head: Vec<&i32> = it.by_ref().take_while(|n| **n < 3).collect();
assert_eq!(head, [&1, &2]);
assert_eq!(it.next(), Some(&1));   // where's the 5? take_while used it up

21. The Custom Rank

You want the "best" item in a list, where "best" is defined by a property you can extract -- the largest file, the most recent date, the shortest name. 

let largest = files.iter().max_by_key(|f| f.size_bytes());
let most_recent = events.iter().max_by_key(|e| e.timestamp);
let shortest_name = users.iter().min_by_key(|u| u.name.len());

max_by_key and min_by_key let you point at a field or derived value and say "compare by this." No need to implement Ord on the whole struct. If you need more complex comparison logic (multi-field tiebreaking), use max_by with a full comparator closure instead.

Clarification Ties, empty input and float keys

Three things the names don't tell you. On a tie, max_by_key returns the last maximum and min_by_key the first minimum. Empty input gives None. And a float key won't compile, because f64 isn't Ord (NaN has no place in the order).

let words = ["bb", "a", "cc", "d"];

assert_eq!(words.iter().max_by_key(|w| w.len()), Some(&"cc"));   // the last of the longest
assert_eq!(words.iter().min_by_key(|w| w.len()), Some(&"a"));    // the first of the shortest

let empty: [&str; 0] = [];
assert_eq!(empty.iter().max_by_key(|w| w.len()), None);

let sizes = [2.5_f64, 9.1, 4.0];
// sizes.iter().max_by_key(|s| **s)
// error[E0277]: the trait bound `f64: Ord` is not satisfied
let biggest = sizes.iter().max_by(|a, b| a.total_cmp(b));
assert_eq!(biggest, Some(&9.1));

22. The Nested Flattening

You have a list of things, each containing its own list. You want one flat list of all the sub-items. 

let all_tags: Vec<&str> = posts.iter()
    .flat_map(|p| &p.tags)
    .map(String::as_str)
    .collect();
// [{tags: ["rust", "cli"]}, {tags: ["wasm"]}] -> ["rust", "cli", "wasm"]

flat_map is map followed by flatten. Each element produces an iterator (or something that can become one), and the results are concatenated into a single stream. It's the iterator equivalent of a nested loop, flattened.

Clarification What flat_map yields here

&p.tags is a &Vec<String>, and iterating over that yields &String. collect won't turn &String into &str for you, so the chain above needs the .map(String::as_str).

struct Post { tags: Vec<String> }
let posts = [
    Post { tags: vec!["rust".into(), "cli".into()] },
    Post { tags: vec!["wasm".into()] },
];

let refs: Vec<&String> = posts.iter().flat_map(|p| &p.tags).collect();
let strs: Vec<&str> = refs.iter().map(|s| s.as_str()).collect();
assert_eq!(strs, ["rust", "cli", "wasm"]);

// let strs: Vec<&str> = posts.iter().flat_map(|p| &p.tags).collect();
// error[E0277]: a value of type `Vec<&str>` cannot be built from an iterator
//               over elements of type `&String`

// flat_map(f) is map(f).flatten()
let same: Vec<&String> = posts.iter().map(|p| &p.tags).flatten().collect();
assert_eq!(refs, same);

// f can return anything iterable, a range for example
let counts: Vec<u32> = (1..=3).flat_map(|n| 0..n).collect();
assert_eq!(counts, [0, 0, 1, 0, 1, 2]);

23. The Index-Aware Transformation

You're processing a list and you need to know each element's position -- for numbering output, building an index, or treating the first/last element differently. 

for (i, line) in lines.iter().enumerate() {
    println!("{:4}: {}", i + 1, line);
}

// Or in a chain:
let numbered: Vec<String> = items.iter()
    .enumerate()
    .map(|(i, item)| format!("{}. {}", i + 1, item))
    .collect();
// ["apple", "banana"] -> ["1. apple", "2. banana"]

enumerate() wraps each element in a (index, element) tuple, starting from zero. It's the Rust equivalent of the "for i, item in enumerate(items)" pattern from Python.

Clarification What {:4} means

The {:4} in the println! is a width: pad to at least four characters. Numbers line up on the right and strings on the left unless you say otherwise. Some format specs, checked with format!:

assert_eq!(format!("{:4}|", 7), "   7|");          // width 4: numbers align right
assert_eq!(format!("{:4}|", "ab"), "ab  |");       // strings align left
assert_eq!(format!("{:<4}|", 7), "7   |");         // < left
assert_eq!(format!("{:^5}|", 7), "  7  |");        // ^ centre
assert_eq!(format!("{:>4}|", "ab"), "  ab|");      // > right
assert_eq!(format!("{:04}", 7), "0007");           // 0 pads with zeros
assert_eq!(format!("{:.2}", 1.23456), "1.23");     // .2 is precision
assert_eq!(format!("{:6.2}|", 1.23456), "  1.23|");
let w = 6;
assert_eq!(format!("{:w$}|", 7), "     7|");       // a width from a variable

// Counting from 1 without the + 1: zip with an open-ended range
let lines = ["apple", "banana"];
let numbered: Vec<String> = (1..).zip(lines).map(|(n, l)| format!("{n:>3}: {l}")).collect();
assert_eq!(numbered, ["  1: apple", "  2: banana"]);

24. The Collection Partition

You want to split one list into two: things that pass a test and things that fail it. Both halves matter. 

let (passing, failing): (Vec<_>, Vec<_>) = tests.iter()
    .partition(|t| t.score >= 70);
// scores [95, 40, 70, 55] -> passing: [95, 70], failing: [40, 55]

partition takes a predicate and returns a tuple of two collections. Every element goes into exactly one of them. Note the type annotation -- Rust needs to know what kind of collections to build, since partition works with any type that implements Default and Extend.

Clarification Why partition needs the annotation

Default and Extend just mean "can start empty" and "can be added to". Plenty of types qualify, so the same call can build two Vecs, two HashSets or two Strings, and Rust can't pick for you:

use std::collections::HashSet;

let scores = [95, 40, 70, 55, 95];

let (pass, fail): (Vec<i32>, Vec<i32>) = scores.iter().partition(|&&s| s >= 70);
assert_eq!(pass, [95, 70, 95]);
assert_eq!(fail, [40, 55]);

let (pass, _): (HashSet<i32>, HashSet<i32>) = scores.iter().partition(|&&s| s >= 70);
assert_eq!(pass.len(), 2);   // the two 95s became one

let (digits, letters): (String, String) = "a1b2c3".chars().partition(|c| c.is_ascii_digit());
assert_eq!((digits.as_str(), letters.as_str()), ("123", "abc"));

// Leave the types out and the compiler asks:
// let (pass, fail) = scores.iter().partition(|&&s| s >= 70);
// error[E0283]: type annotations needed for `(_, _)`

25. The Double-Ended Extraction

You need the first and last elements of a collection. Not the min and max -- the actual first and last by position. 

let mut it = items.iter();      // items = [10, 20, 30]
let first = it.next();         // Some(&10)
let last = it.next_back();     // Some(&30)

This works because slice::Iter implements DoubleEndedIterator, which gives you next_back(). The two calls don't interfere -- next pulls from the front, next_back pulls from the back. If the collection has only one element, last will be None.

Clarification Slices already know their ends

On a slice or Vec, first() and last() do this without an iterator. They differ from the iterator version for a single element: an iterator hands each item out once, so next and next_back can't both get it.

let items = [10, 20, 30];
assert_eq!(items.first(), Some(&10));
assert_eq!(items.last(), Some(&30));
assert_eq!(items.split_first(), Some((&10, &[20, 30][..])));

let one = [10];
assert_eq!((one.first(), one.last()), (Some(&10), Some(&10)));   // both see it
let mut it = one.iter();
assert_eq!((it.next(), it.next_back()), (Some(&10), None));      // only one gets it

// The two ends close in on each other
let four = [1, 2, 3, 4];
let mut it = four.iter();
assert_eq!(it.next(), Some(&1));
assert_eq!(it.next_back(), Some(&4));
assert_eq!(it.as_slice(), [2, 3]);   // what's left in between

26. The Pair Walk

You have two lists of the same length and you want to process them element-by-element in lockstep. 

let names = vec!["Alice", "Bob", "Carol"];
let scores = vec![95, 87, 92];

let report: Vec<String> = names.iter()
    .zip(scores.iter())
    .map(|(name, score)| format!("{name}: {score}"))
    .collect();
// -> ["Alice: 95", "Bob: 87", "Carol: 92"]

zip pairs up elements from two iterators, producing (a, b) tuples. It stops when the shorter iterator runs out -- no panics, no padding, just a clean stop. If you need to know about the leftovers, look at zip_longest from the itertools crate.

Clarification zip drops leftovers silently

zip stops as soon as either side runs out, with no warning, so a length mismatch just loses data. The second argument can be anything iterable, and unzip goes the other way.

let names = ["Alice", "Bob", "Carol"];
let scores = [95, 87];                               // one short

let pairs: Vec<(&&str, &i32)> = names.iter().zip(scores.iter()).collect();
assert_eq!(pairs, [(&"Alice", &95), (&"Bob", &87)]); // Carol is gone
assert_eq!(pairs.len(), names.len().min(scores.len()));

let same: Vec<(&&str, &i32)> = names.iter().zip(&scores).collect();   // no .iter() needed
assert_eq!(pairs, same);

// unzip splits pairs back into two collections
let (n, s): (Vec<&str>, Vec<i32>) = [("Al", 1), ("Bo", 2)].into_iter().unzip();
assert_eq!(n, ["Al", "Bo"]);
assert_eq!(s, [1, 2]);

27. The Chain Link

You have two collections of the same type and you want to process them as one continuous sequence. 

let defaults = vec!["debug", "info"];
let overrides = vec!["warn", "error"];

let all_levels: Vec<_> = defaults.iter()
    .chain(overrides.iter())
    .collect();
// ["debug", "info", "warn", "error"]

chain appends one iterator after another. When the first runs out, it seamlessly switches to the second. You can chain as many as you want: a.chain(b).chain(c). It's lazy -- nothing happens until you consume the chained iterator.

Clarification Nothing runs until something pulls

Building a chain of adapters does no work. Items are pulled through one at a time when the consumer at the end asks for them, and only as many as it asks for. A counter shows it (the Cell lets the closure count while we read):

use std::cell::Cell;

let pulled = Cell::new(0);
let a = [1, 2];
let b = [3, 4];

let chain = a.iter()
    .chain(&b)
    .inspect(|_| pulled.set(pulled.get() + 1));
assert_eq!(pulled.get(), 0);                 // built, but nothing has run

let first_three: Vec<&i32> = chain.take(3).collect();
assert_eq!(first_three, [&1, &2, &3]);
assert_eq!(pulled.get(), 3);                 // only what take(3) asked for: 4 was never touched

28. The Existence Probe

You don't need the matching element. You just need to know: does any element match? Or do all of them match? 

let has_errors = results.iter().any(|r| r.is_err());
// [Ok(1), Err(e), Ok(3)] -> true   (stops at Err)
let all_positive = numbers.iter().all(|&n| n > 0);
// [3, -1, 5] -> false              (stops at -1)

Both any and all short-circuit. any returns true the moment it finds a match and stops. all returns false the moment it finds a non-match and stops. They're the iterator equivalent of || and && across a collection.

Clarification any and all on an empty iterator

On an empty iterator, any is false (nothing matched) and all is true (nothing failed). That's what you get by treating them as || and && across the items, starting from false and true.

let empty: [i32; 0] = [];
assert_eq!(empty.iter().any(|&n| n < 0), false);
assert_eq!(empty.iter().all(|&n| n < 0), true);   // "every one of none" is true

// any = false || p(a) || p(b) || ...    all = true && p(a) && p(b) && ...
assert_eq!([3, -1, 5].iter().any(|&n| n < 0), false || 3 < 0 || -1 < 0 || 5 < 0);
assert_eq!([3, -1, 5].iter().all(|&n| n > 0), true && 3 > 0 && -1 > 0 && 5 > 0);

// Like || and &&, they stop as soon as the answer is known
let mut looked_at = Vec::new();
let found = [3, -1, 5].iter().any(|&n| { looked_at.push(n); n < 0 });
assert!(found);
assert_eq!(looked_at, [3, -1]);   // 5 was never checked

29. The Accumulator

You need to reduce a collection down to a single value, and the reduction is more complex than a simple sum or product. 

// Build a frequency map
let freq = words.iter().fold(HashMap::new(), |mut map, word| {
    *map.entry(word).or_insert(0) += 1;
    map
});

// Concatenate with a separator
let csv = fields.iter().fold(String::new(), |mut acc, field| {
    if !acc.is_empty() { acc.push(','); }
    acc.push_str(field);
    acc
});

fold takes an initial value (the "accumulator") and a closure that combines the accumulator with each element. It's the general-purpose reduction -- sum, product, count, min, and max are all special cases of fold. If you don't need an initial value, reduce starts with the first element instead.

Clarification fold vs reduce, and which way they run

fold starts from the value you give it; reduce starts from the first item, so on an empty iterator all it can return is None. Both run left to right, which a step where the order matters makes visible:

let digits = [1, 2, 3];

// fold goes left to right: ((0*10 + 1)*10 + 2)*10 + 3
assert_eq!(digits.iter().fold(0, |acc, d| acc * 10 + d), 123);
assert_eq!(digits.iter().rfold(0, |acc, d| acc * 10 + d), 321);   // rfold: right to left

assert_eq!(digits.iter().copied().reduce(|a, b| a + b), Some(6));

let empty: [i32; 0] = [];
assert_eq!(empty.iter().fold(0, |acc, d| acc + d), 0);            // you get the seed back
assert_eq!(empty.iter().copied().reduce(|a, b| a + b), None);    // nothing to start from

// The comma-separated fold above has a shortcut on slices
assert_eq!(["x", "y", "z"].join(","), "x,y,z");

30. The Windowed View

You need to look at consecutive groups of elements -- pairs, triples, or sliding windows of any size. 

let data = vec![1, 2, 3, 4, 5];

// Sliding windows of size 2
for pair in data.windows(2) {
    println!("{} -> {}", pair[0], pair[1]);
}
// 1 -> 2, 2 -> 3, 3 -> 4, 4 -> 5

// Fixed-size chunks (non-overlapping)
for chunk in data.chunks(2) {
    println!("{:?}", chunk);
}
// [1, 2], [3, 4], [5]

windows gives you overlapping slices -- every contiguous group of n elements. chunks gives you non-overlapping slices -- the list cut into pieces of size n (the last one might be shorter). Both return slices, not copies.

Clarification How many windows, how many chunks

For a slice of length len, windows(n) yields len - n + 1 windows, or none at all if the slice is shorter than n. chunks(n) yields len / n rounded up, and the last one may be short. chunks_exact keeps only the full chunks and sets the rest aside.

let data = [1, 2, 3, 4, 5];

let windows: Vec<&[i32]> = data.windows(2).collect();
assert_eq!(windows, [[1, 2], [2, 3], [3, 4], [4, 5]]);   // 5 - 2 + 1 = 4 windows
assert_eq!(data.windows(6).count(), 0);                  // too short: no windows at all

let chunks: Vec<&[i32]> = data.chunks(2).collect();
assert_eq!(chunks, [&[1, 2][..], &[3, 4], &[5]]);        // 5 / 2 rounded up; the last is short

let exact = data.chunks_exact(2);
assert_eq!(exact.remainder(), [5]);                      // set aside
assert_eq!(exact.count(), 2);                            // only the full chunks

// data.windows(0)   // panics: window size must be non-zero

// A typical job for windows: differences between neighbours
let deltas: Vec<i32> = [1, 4, 9, 16].windows(2).map(|w| w[1] - w[0]).collect();
assert_eq!(deltas, [3, 5, 7]);

31. The Unique Run

You have a sorted (or partially sorted) list and you want to remove consecutive duplicates. 

let mut data = vec![1, 1, 2, 3, 3, 3, 4];
data.dedup();
// [1, 2, 3, 4]

// Dedup by a key (e.g., ignore case)
let mut words = vec!["Hello", "hello", "World", "world"];
words.dedup_by_key(|s| s.to_lowercase());
// ["Hello", "World"]

dedup removes consecutive duplicates in place. It doesn't sort first -- it only collapses runs of identical values. If you need globally unique values, sort first, then dedup. Or use a HashSet if order doesn't matter.

Clarification Only next-door duplicates

dedup compares each item with the one before it, so duplicates that aren't next to each other survive. Sort first for unique values in sorted order, or use a HashSet to keep the order they first appeared in.

let mut v = vec![3, 1, 3, 3, 1];
v.dedup();
assert_eq!(v, [3, 1, 3, 1]);              // only the 3, 3 run collapsed

let mut v = vec![3, 1, 3, 3, 1];
v.sort();                                 // [1, 1, 3, 3, 3]
v.dedup();
assert_eq!(v, [1, 3]);                    // unique, in sorted order

use std::collections::HashSet;
let mut seen = HashSet::new();
let mut v = vec![3, 1, 3, 3, 1];
v.retain(|x| seen.insert(*x));            // insert returns false for a repeat
assert_eq!(v, [3, 1]);                    // unique, in first-seen order

// To get the runs themselves, chunk_by (Rust 1.77) groups them
let runs: Vec<&[i32]> = [1, 1, 2, 3, 3, 3].chunk_by(|a, b| a == b).collect();
assert_eq!(runs, [&[1, 1][..], &[2], &[3, 3, 3]]);

32. The Position Finder

You don't need the element itself. You need to know where it is. 

let idx = haystack.iter().position(|&x| x == needle);
// Some(3) or None

let last_idx = haystack.iter().rposition(|&x| x == needle);
// searches from the end

position returns the index of the first match. rposition returns the index of the last match (searching backward). Both return Option<usize> -- None if no element matches. These are the iterator equivalent of indexOf from other languages, but with a predicate instead of just equality.

Clarification rposition still counts from the front

rposition searches from the back but reports the index from the front, the one you'd use with v[i]. Reverse the iterator first if you want the distance from the back.

let v = [7, 2, 9, 2, 5];

assert_eq!(v.iter().position(|&x| x == 2), Some(1));
assert_eq!(v.iter().rposition(|&x| x == 2), Some(3));        // v[3] is the last 2
assert_eq!(v.iter().rev().position(|&x| x == 2), Some(1));   // one step in from the end
assert_eq!(v.iter().position(|&x| x == 4), None);

// For plain equality, slices have a shortcut
assert!(v.contains(&9));

// On sorted data, binary_search says where it is, or where it would go
let sorted = [1, 3, 5, 7];
assert_eq!(sorted.binary_search(&5), Ok(2));
assert_eq!(sorted.binary_search(&4), Err(2));   // not there; it would go at index 2

IV. Composition

These patterns are about combining operations cleanly -- chaining fallible operations, injecting side effects without breaking chains, and flipping container types to match what the surrounding code expects.

33. The Fallible Map

You have a Result and you want to run another operation that could also fail. If you use map, you end up with Result<Result<T, E>, E> -- a nested mess. You want flat chaining. 

let content = find_file(name)
    .and_then(|path| read_to_string(path))?;
// Ok("config.toml") -> read_to_string("config.toml") -> Ok("key = val")
// Err(e)            -> Err(e)   (skips read_to_string entirely)

and_then is the monadic bind for Result (and Option). If the first operation succeeds, it feeds the value to the next function. If it fails, it short-circuits with the error. It's map but the closure itself returns a Result, and the nesting is flattened automatically.

On Option, and_then does the same thing -- it's how you chain functions that return Option without ending up with Option<Option<T>>.

Clarification and_then passes errors through unchanged

With map, a step that returns a Result leaves a Result inside a Result; and_then flattens it. Both steps must share an error type, because and_then passes errors through as they are. When the types differ, ? can convert them (see the box under #2).

fn parse(s: &str) -> Result<i32, String> {
    s.parse().map_err(|_| format!("not a number: {s}"))
}
fn non_zero(n: i32) -> Result<i32, String> {
    if n != 0 { Ok(n) } else { Err(String::from("zero")) }
}

assert_eq!(parse("5").map(non_zero), Ok(Ok(5)));                    // nested
assert_eq!(parse("5").and_then(non_zero), Ok(5));                   // flat
assert_eq!(parse("0").and_then(non_zero), Err(String::from("zero")));
// "x" fails in parse, so non_zero never runs
assert_eq!(parse("x").and_then(non_zero), Err(String::from("not a number: x")));

// Two different error types: ? converts both into Box<dyn Error>
use std::error::Error;
fn checked(s: &str) -> Result<i32, Box<dyn Error>> {
    let n: i32 = s.parse()?;   // ParseIntError
    Ok(non_zero(n)?)           // String
}
assert_eq!(checked("5").unwrap(), 5);
assert_eq!(checked("0").unwrap_err().to_string(), "zero");
assert_eq!(checked("x").unwrap_err().to_string(), "invalid digit found in string");

34. The In-Place Wrapper Removal

You used a BufReader, a GzDecoder, or some other wrapper type to add behavior to an inner resource. Now you're done with the wrapper and want the original back. 

let file = buf_reader.into_inner();
let socket = tls_stream.into_inner();

into_inner() is the standard Rust name for "give me the thing inside this wrapper." The into_ prefix tells you it consumes the wrapper. What happens to buffered data depends on the wrapper: a BufReader throws away anything it read ahead, while a BufWriter writes its buffer out first, which is why its into_inner returns a Result.

Clarification What happens to the buffered data

Both halves of that last sentence, made visible with a Cursor under the reader and a Vec under the writer:

use std::io::{BufReader, BufWriter, Cursor, Read, Write};

let mut reader = BufReader::with_capacity(4, Cursor::new(b"abcdefgh".to_vec()));
let mut first = [0u8; 1];
reader.read_exact(&mut first).unwrap();      // reads 4 bytes ahead, hands out 1
assert_eq!(&first, b"a");
assert_eq!(reader.buffer(), b"bcd");         // read, but not handed out yet
let cursor = reader.into_inner();
assert_eq!(cursor.position(), 4);            // b, c and d went down with the wrapper

let mut writer = BufWriter::new(Vec::new());
writer.write_all(b"hi").unwrap();
assert!(writer.get_ref().is_empty());        // still in BufWriter's buffer
let bytes = writer.into_inner().unwrap();    // written out first, and that can fail
assert_eq!(bytes, b"hi");

35. The Peek and Poke

You're building a long method chain and something isn't working. You want to see what's flowing through at a specific point without breaking the chain. 

let total = items.iter()
    .filter(|x| x.is_valid())
    .inspect(|x| eprintln!("after filter: {x:?}"))
    .map(|x| x.value())
    .inspect(|v| eprintln!("after map: {v}"))
    .sum::<i32>();

inspect passes a reference to each element to a closure, then passes the element through unchanged. It's println-debugging for iterator chains. In production code, you'll see it with logging instead of printing.

On Result, there's inspect and inspect_err for peeking at the success and error sides independently.

Clarification {x:?} and dbg!

{x:?} is {:?} with the variable named inside the braces. For quick looks there's also dbg!: it prints the expression and its value to stderr, then returns the value, so it fits inside a chain the way inspect does.

let x = (1, "a");
assert_eq!(format!("{x:?}"), r#"(1, "a")"#);                // Debug formatting
assert_eq!(format!("{x:?}"), format!("{:?}", x));           // named inside, or passed after
assert_eq!(format!("{x:#?}"), "(\n    1,\n    \"a\",\n)");  // # pretty-prints

let total: i32 = [1, 2, 3].iter().map(|n| dbg!(n * 10)).sum();
assert_eq!(total, 60);
// stderr: [src/main.rs:...] n * 10 = 10, then 20, then 30

// Option and Result have inspect too (Rust 1.76)
let mut seen = None;
let doubled = Some(4).inspect(|v| seen = Some(*v)).map(|v| v * 2);
assert_eq!((seen, doubled), (Some(4), Some(8)));

36. The Type Flip

You have an Option<Result<T, E>> -- maybe from a function that optionally does something fallible. But your function returns Result, so you want Result<Option<T>, E> instead, so you can use ? on the outer layer. 

fn get_config_value(key: &str) -> Result<Option<String>, ConfigError> {
    let maybe_raw: Option<Result<String, ConfigError>> = map.get(key).map(parse);
    maybe_raw.transpose()
    // Option<Result<T, E>> -> Result<Option<T>, E>
}

transpose swaps the container types. If the Option is None, you get Ok(None). If it's Some(Ok(v)), you get Ok(Some(v)). If it's Some(Err(e)), you get Err(e). It works in the other direction too -- Result<Option<T>, E> back to Option<Result<T, E>>.

Clarification transpose, all three cases

An Option<Result<T, E>> has only three possible shapes, so here's each one, the round trip, and the most common real use: an optional setting that might fail to parse.

let a: Option<Result<i32, String>> = None;
let b: Option<Result<i32, String>> = Some(Ok(1));
let c: Option<Result<i32, String>> = Some(Err(String::from("bad")));

assert_eq!(a.transpose(), Ok(None));
assert_eq!(b.transpose(), Ok(Some(1)));
assert_eq!(c.transpose(), Err(String::from("bad")));

let r: Result<Option<i32>, String> = Ok(Some(1));
assert_eq!(r.clone().transpose(), Some(Ok(1)));
assert_eq!(r.clone().transpose().transpose(), r);   // flipping twice gets you back

fn port(raw: Option<&str>) -> Result<Option<u16>, std::num::ParseIntError> {
    raw.map(str::parse::<u16>).transpose()
}
assert_eq!(port(None), Ok(None));                  // not set: fine
assert_eq!(port(Some("8080")), Ok(Some(8080)));
assert!(port(Some("http")).is_err());              // set, but invalid: an error

37. The Lazy Default

If a value is missing, you need a default -- but that default involves a heap allocation or a computation you don't want to do unless you have to. 

// This allocates every time, even when the Option is Some:
let name = opt_name.unwrap_or(String::from("Anonymous"));

// This only allocates when the Option is None:
let name = opt_name.unwrap_or_else(|| String::from("Anonymous"));

The _or vs _or_else distinction is one of Rust's core naming conventions (covered in the companion post). Eager vs lazy. Value vs closure. Whenever the fallback involves allocation, I/O, or anything more than returning a literal, reach for the _else variant.

Clarification When the argument runs

Rust evaluates arguments before the call, so unwrap_or(make()) runs make() even when the value isn't needed. Passing a closure doesn't run it; unwrap_or_else calls it only on None. Counting the calls:

use std::cell::Cell;

let calls = Cell::new(0);
let make = || {
    calls.set(calls.get() + 1);
    String::from("Anonymous")
};

let name = Some(String::from("Ann"));
let _ = name.clone().unwrap_or(make());      // make() ran, and its String was thrown away
assert_eq!(calls.get(), 1);
let _ = name.clone().unwrap_or_else(make);   // the closure was passed, never called
assert_eq!(calls.get(), 1);
let _ = None.unwrap_or_else(make);           // called, because it was needed
assert_eq!(calls.get(), 2);

// Only some defaults cost anything to make
assert_eq!(String::new().capacity(), 0);              // no allocation
assert!(String::from("Anonymous").capacity() >= 9);   // a heap allocation

38. The Slot Machine

You're building up a HashMap and you need to handle the "insert if missing, update if present" logic cleanly. The entry API gives you a handle to a slot, and then you decide what to do with it. 

use std::collections::HashMap;

let mut counts: HashMap<&str, i32> = HashMap::new();

for word in words {
    *counts.entry(word).or_insert(0) += 1;
}

// or_insert_with for expensive defaults:
let mut cache: HashMap<String, Vec<Data>> = HashMap::new();
let items = cache.entry(key.clone())
    .or_insert_with(|| load_from_disk(&key));

entry() returns an Entry enum -- either Occupied or Vacant. Then or_insert fills the vacant slot, or or_insert_with computes the value lazily. The whole thing gives you a mutable reference to the value, whether it was just inserted or already there. It's a single hash lookup instead of the two (check then insert) you'd need otherwise.

Clarification Why the *

or_insert returns &mut V, a reference to the value in the map, so += 1 needs a * to write through it. The other Entry methods follow the same shape.

use std::collections::HashMap;

let mut counts: HashMap<&str, i32> = HashMap::new();

let slot: &mut i32 = counts.entry("a").or_insert(0);   // a reference into the map
*slot += 1;                                            // * writes through it
*counts.entry("a").or_insert(0) += 1;                  // the same, in one line
assert_eq!(counts["a"], 2);

*counts.entry("b").or_default() += 1;                  // or_default starts from i32::default()
assert_eq!(counts["b"], 1);

// and_modify runs only if the key is there, or_insert only if it isn't
counts.entry("a").and_modify(|n| *n *= 10).or_insert(100);
counts.entry("c").and_modify(|n| *n *= 10).or_insert(100);
assert_eq!((counts["a"], counts["c"]), (20, 100));

39. The Turbofish

Rust can usually infer types, but sometimes it can't. You need to tell it explicitly, and the syntax for that looks like a fish: ::<Type>. 

let x = "42".parse::<i32>()?;                                    // Ok(42)
let nums = vec![1, 2, 3].into_iter().collect::<HashSet<_>>();  // {1, 2, 3}
let total = values.iter().sum::<f64>();                           // e.g. 10.5

The turbofish appears when a method is generic and the return type isn't constrained by context. parse can return anything that implements FromStr, collect can build anything that implements FromIterator, and sum can return any numeric type. The turbofish disambiguates. The alternative is a type annotation on the variable: let x: i32 = "42".parse()?; -- same effect, different style.

Clarification Where the ::<> goes

The turbofish goes on whatever has the type parameter: a method (parse::<T>), a type (Vec::<T>::new) or a function (size_of::<T>). The :: is needed because without it, < reads as less-than.

use std::collections::BTreeSet;

assert_eq!("42".parse::<i32>(), Ok(42));                    // on a method
assert_eq!("42".parse::<u8>().map(|n| n + 1), Ok(43));
let v = Vec::<u8>::with_capacity(4);                        // on a type
assert!(v.capacity() >= 4);
assert_eq!(std::mem::size_of::<u64>(), 8);                  // on a function
assert_eq!([1, 2, 3].iter().sum::<i32>(), 6);

let set = [3, 1, 3].into_iter().collect::<BTreeSet<_>>();   // _ means "work this part out"
assert_eq!(set.into_iter().collect::<Vec<_>>(), [1, 3]);

// Without the ::, it's a comparison:
// let x = "42".parse<i32>();
// error: comparison operators cannot be chained

40. The Scope Guard

You need to run cleanup code when a value is dropped, regardless of whether the function returns normally or panics. Rust's Drop trait is the tool, and it works even on early returns from ?. 

struct TempFile(PathBuf);

impl Drop for TempFile {
    fn drop(&mut self) {
        let _ = std::fs::remove_file(&self.0);
    }
}

fn process() -> Result<(), Error> {
    let tmp = TempFile(create_temp_file()?);
    do_something_fallible()?;   // if this fails, tmp is still cleaned up
    do_another_thing()?;        // same here
    Ok(())
    // tmp dropped here on success
}

This is Rust's answer to try/finally, defer, and RAII. The Drop implementation runs when the value goes out of scope -- whether that's at the end of the function, after a ? early return, or during a panic unwind. You don't call it. You can't forget it.

Clarification let _ = ... drops immediately

The Drop impl uses let _ = ... to ignore a Result, which is fine. But _ isn't a variable: it binds nothing, so a guard assigned to _ is dropped at the end of that statement. Give a guard a name, even _guard, to keep it until the end of the scope. Named values are dropped in reverse order:

use std::cell::RefCell;

struct Noisy<'a>(&'static str, &'a RefCell<Vec<&'static str>>);
impl Drop for Noisy<'_> {
    fn drop(&mut self) {
        self.1.borrow_mut().push(self.0);
    }
}

let log = RefCell::new(Vec::new());
{
    let _a = Noisy("a", &log);
    let _b = Noisy("b", &log);
    let _ = Noisy("temp", &log);   // _ binds nothing: dropped right here
    log.borrow_mut().push("end of block");
}                                  // then _b, then _a: reverse order
assert_eq!(*log.borrow(), ["temp", "end of block", "b", "a"]);

let early = Noisy("early", &log);
drop(early);                       // or end it yourself, whenever you like
assert_eq!(log.borrow().last(), Some(&"early"));

Putting It All Together

Knowing forty patterns individually is like knowing forty words in a foreign language. You can point at things. You can't hold a conversation. The real skill is seeing how they combine -- recognizing that the problem in front of you is a three-pattern problem, and knowing which three.

Let's work through this in layers, from small combinations to real-world functions, and then look at how you'd arrive at these combinations yourself.

Small Combinations: Two or Three Patterns

Validate and collect. You have raw string inputs. You want the valid ones parsed, the garbage silently dropped, and a count of how many you kept. 

let valid: Vec<i32> = raw_inputs.iter()
    .filter_map(|s| s.parse().ok())  // #3: Silent Discard
    .collect();
// ["10", "abc", "20", ""] -> [10, 20]

let kept = valid.len(); // 2

Two patterns. The Silent Discard (#3) does the filtering and parsing in one step. collect gathers the survivors. If you'd written this as a loop, you'd have a mutable vec, a match statement, and a counter. Here, the intent is one line.

Lookup with a computed fallback. You're checking a cache. If the key isn't there, you compute the value (which involves I/O), store it, and return it. 

let entry = cache.entry(key.clone())       // #38: Slot Machine
    .or_insert_with(|| fetch_from_db(&key)); // #37: Lazy Default

The Slot Machine (#38) gives you a handle to the map slot. The Lazy Default (#37) ensures you only hit the database on a cache miss. One hash lookup, zero redundant I/O. The _with suffix is doing real work here -- without it, you'd call fetch_from_db on every access regardless.

Find the best match and borrow its data. You want the user with the highest score, and you want their name -- but you don't want to take ownership of anything. 

let top_name = users.iter()
    .max_by_key(|u| u.score)    // #21: Custom Rank
    .map(|u| u.name.as_str());  // #10: Map the Wrapper + borrowing
// [{name: "Alice", score: 90}, {name: "Bob", score: 95}] -> Some("Bob")

Custom Rank (#21) finds the winner. Map the Wrapper (#10) reaches inside the Option to extract what you actually care about. The result is Option<&str> -- no cloning, no ownership transfer.

Medium Scale: The Daily Function

Here's a function you'd actually write. You're loading plugin configs from a directory. Some files might not exist (that's fine -- they're optional). Some might exist but contain garbage (that's an error). You want the valid configs, with the bad files reported. 

fn load_plugins(dir: &Path) -> Result<Vec<PluginConfig>, AppError> {
    let entries: Vec<_> = std::fs::read_dir(dir)
        .map_err(|e| AppError::DirRead { path: dir.into(), source: e })?  // #4: Specific Failure Context
        .filter_map(|entry| entry.ok())  // #3: Silent Discard (bad dir entries)
        .filter(|entry| {
            entry.path()
                .extension()
                .and_then(|ext| ext.to_str())          // #33: Fallible Map
                .is_some_and(|ext| ext == "toml")      // #8: Conditional Keep (conceptually)
        })
        .collect();

    entries.iter()
        .map(|entry| {
            let path = entry.path();
            let text = std::fs::read_to_string(&path)
                .map_err(|e| AppError::FileRead {     // #4: Specific Failure Context
                    path: path.clone(), source: e
                })?;
            toml::from_str(&text)
                .map_err(|e| AppError::ParseConfig {  // #4 again
                    path: path.clone(), source: e
                })
        })
        .collect()  // #1: Success or Bail
}

Count the patterns: Silent Discard for filesystem noise, Specific Failure Context twice (once for I/O, once for parsing), Fallible Map to chain the extension check, and Success or Bail at the end to turn the iterator of Results into a single Result.

Now look at what you didn't write. No nested match statements. No mutable error vec. No boolean flag tracking whether something went wrong. The control flow is declared, not managed.

Across Pattern Groups: Ownership Meets Iteration Meets Error Handling

The interesting functions are the ones where patterns from different sections collide. Here's a config merger: you have a HashMap of default settings and a HashMap of user overrides. If the user's value requires normalization (which can fail), you want to normalize it. Otherwise, fall back to the default. Bad user values should report errors, not silently corrupt the config. 

fn merge_config(
    defaults: &HashMap<String, String>,
    overrides: HashMap<String, String>,  // owned -- we're consuming this
) -> Result<HashMap<String, String>, ConfigError> {
    let mut merged = defaults.clone();

    for (key, raw_value) in overrides.into_iter() {  // #13: Resource Recycle
        let normalized = normalize(&raw_value)
            .map_err(|e| ConfigError::BadOverride {  // #4: Specific Failure Context
                key: key.clone(),
                source: e,
            })?;

        merged.entry(key)            // #38: Slot Machine
            .and_modify(|v| *v = normalized.clone())
            .or_insert(normalized);
    }

    Ok(merged)
}

Resource Recycle (#13) consumes the overrides map so we get owned keys and values -- no unnecessary cloning of strings we already own. Specific Failure Context (#4) attaches the offending key to any normalization error. The Slot Machine (#38) handles both "key exists, update it" and "key is new, insert it" without a double lookup.

The Conditional Processing Pipeline

Here's a pattern that shows up in anything that processes heterogeneous data: events, log lines, HTTP requests. You have a stream of items, some need transformation, some pass through unchanged, and you want to avoid allocating when you don't have to. 

use std::borrow::Cow;

fn process_log_lines<'a>(lines: &'a [String]) -> Vec<Cow<'a, str>> {
    lines.iter()
        .filter(|line| !line.is_empty())                      // skip blanks
        .enumerate()                                          // #23: Index-Aware
        .map(|(i, line)| {
            if line.contains('\t') {
                Cow::Owned(format!("[{}] {}", i, line.replace('\t', "  ")))  // #18: Cow Dance
            } else {
                Cow::Borrowed(line.as_str())                  // #18: no allocation
            }
        })
        .collect()
}

The Cow Dance (#18) means that clean lines -- which are most of them -- involve zero heap allocation. Only the lines that need modification pay for it. The Index-Aware pattern (#23) gives us line numbers for the reformatted output. If this were processing a million log lines, the difference between "clone everything" and "clone only what changes" is measured in milliseconds and megabytes.

The Before and After

Patterns matter most when you see what code looks like without them. Here's a function written by someone who knows Rust syntax but hasn't internalized the patterns: 

// Before: manual, verbose, fragile
fn find_best_valid_score(entries: &[Entry]) -> Result<Option<i64>, ScoreError> {
    let mut best: Option<i64> = None;
    for entry in entries {
        match entry.raw_score {
            Some(raw) => {
                match validate_score(raw) {
                    Ok(valid) => {
                        match best {
                            Some(current) if valid > current => best = Some(valid),
                            None => best = Some(valid),
                            _ => {}
                        }
                    }
                    Err(e) => return Err(ScoreError::Validation {
                        id: entry.id, source: e
                    }),
                }
            }
            None => {} // skip entries without scores
        }
    }
    Ok(best)
}

Three levels of nesting. A mutable accumulator. An empty match arm that exists only because match is exhaustive. It works, but it makes you trace every branch to understand what it does.

Now the same function with patterns: 

// After: declarative, flat, same behavior
fn find_best_valid_score(entries: &[Entry]) -> Result<Option<i64>, ScoreError> {
    entries.iter()
        .filter_map(|e| {                                    // #3: Silent Discard (None scores)
            e.raw_score.map(|raw| (e.id, raw))               // #10: Map the Wrapper
        })
        .map(|(id, raw)| {
            validate_score(raw)
                .map_err(|e| ScoreError::Validation {        // #4: Specific Failure Context
                    id, source: e
                })
        })
        .collect::<Result<Vec<_>, _>>()?                     // #1: Success or Bail
        .into_iter()                                         // #13: Resource Recycle
        .max()                                               // largest valid score
        .pipe(Ok)                                            // wrap in Ok -- or just:
        // Ok(scores.into_iter().max())                      // if you collected first
}

Clarification .pipe isn't in the standard library

pipe comes from the tap crate, which adds it to every type: x.pipe(f) is just f(x), so a chain can end by handing its result to Ok. Without the crate, the version above doesn't compile; the next version avoids it by wrapping the chain in Ok(...). Here's all pipe does:

trait Pipe: Sized {
    fn pipe<R>(self, f: impl FnOnce(Self) -> R) -> R {
        f(self)
    }
}
impl<T> Pipe for T {}

assert_eq!(5.pipe(|n| n * 2), 10);
let best: Result<Option<i64>, ()> = vec![3_i64, 9, 4].into_iter().max().pipe(Ok);
assert_eq!(best, Ok(Some(9)));

Or, more practically: 

fn find_best_valid_score(entries: &[Entry]) -> Result<Option<i64>, ScoreError> {
    let valid_scores: Vec<i64> = entries.iter()
        .filter_map(|e| e.raw_score.map(|raw| (e.id, raw))) // #3 + #10
        .map(|(id, raw)| {
            validate_score(raw)
                .map_err(|e| ScoreError::Validation { id, source: e }) // #4
        })
        .collect::<Result<Vec<_>, _>>()?;                    // #1

    Ok(valid_scores.into_iter().max())
}

Same logic. Zero nesting. No mutable state. The error handling is precise (which entry failed, and why) without being verbose. And every step in the chain has a name you can point at: "that's a Silent Discard, that's a Specific Failure Context, that's a Success or Bail."

How You Get There: The Decision Process

When you're staring at a function and wondering which patterns apply, there are three questions worth asking:

1. What shape is my data, and what shape do I need?

If you have a collection and want a single value, you're in fold/reduce territory (#29). If you have a collection and want a filtered or transformed collection, you're in the iterator section. If you have a single wrapped value and want to transform what's inside, that's map (#10) or and_then (#33).

2. What can go wrong, and who needs to know?

If failure means "skip this item," that's Silent Discard (#3). If failure means "abort everything," that's Success or Bail (#1). If failure means "add context and propagate," that's Specific Failure Context (#4). If you have an Option but the caller expects a Result, that's Error Pivot (#2). These decisions compose: within a single chain, different steps can handle failure differently.

3. Who owns what?

If you're done with a collection and need its contents, consume it with into_iter (#13). If you're peeking at data inside an Option or smart pointer, use as_deref (#14). If most inputs won't need modification, consider Cow (#18). If you need to take a value out of a mutable struct, that's take (#15). Ownership questions determine whether you're cloning, borrowing, or moving -- and the wrong choice shows up as either a compiler error or a performance problem.

These three questions usually narrow you down to five or six candidate patterns. From there, it's a matter of which ones compose cleanly for your specific case. And that part gets fast with practice -- once you've seen the Slot Machine solve the "insert or update" problem three times, you stop even thinking about it. Your fingers type entry().or_insert the way a C programmer types if (ptr == NULL).

The Bigger Point

None of these patterns are clever. That's the whole point. Each one is a small, obvious decision made explicit. The compound effect of making forty small obvious decisions instead of one large clever one is code that reads like a description of what it does rather than a set of instructions for how to do it.

That's what it means to think in Rust. Not "memorize the Iterator trait." Not "fight the borrow checker." Just: know the forty small decisions, and recognize which ones your function is making.
