When Does Your Code Run? Part 3: Where Does the Error Go?

November 2026

Part 3 of 3 in When Does Your Code Run?

Previous: Part 2: Iterators | Next: none

Part 1 asked when the code you pass to an Option method runs. Result answers that the same way: map runs your closure on Ok, unwrap_or's argument is worked out before the call, and so on.

But a Result carries something an Option doesn't. When there's no value, there's an error instead, and the error has to go somewhere. This part follows it. Two small functions first, used all the way through:

fn parse(s: &str) -> Result<i32, String> {
    s.parse::<i32>().map_err(|e| format!("{s:?}: {e}"))
}

fn half(n: i32) -> Result<i32, String> {
    println!("halving {n}");
    if n % 2 == 0 { Ok(n / 2) } else { Err(format!("{n} is odd")) }
}

parse turns text into a number, and half halves it if it's even. Both can fail. And half announces itself, as noisy did in part 1. Now the puzzle. What does this print, and which inputs get a halving line?

for s in ["8", "7", "x"] {
    let r = parse(s).and_then(half).map(|n| n * 10);
    println!("{r:?}");
}

Hold on to your answer. Section 1 has it.

Every example was compiled with rustc 1.97.0, edition 2024. Compiler errors are cut down to their key lines.

1. An error skips every step that's waiting for Ok

halving 8
Ok(40)
halving 7
Err("7 is odd")
Err("\"x\": invalid digit found in string")

"8" makes it all the way: parsed to 8, halved to 4, multiplied to 40.

"7" parses fine, so half runs, and it fails. From then on, the Result is Err("7 is odd"). map sees the Err, doesn't call its closure, and passes the error on unchanged.

"x" fails at the first step, and there's no halving line. and_then only calls half on Ok, and map only calls its closure on Ok, so the error skips both and comes out the far end exactly as parse made it.

So the first place an error can go is past every step that's waiting for an Ok, untouched. It's the same rule as part 1's map on None. The only difference is that Err has something inside to carry along.

Say it: if it worked, do this next. If it didn't, pass the error on.

2. map_err: the one step that runs on Err

map_err is map's mirror image. It runs your closure on the error, and leaves an Ok alone. parse already uses it. Here's what str::parse gives you without it, next to what parse returns:

Err(ParseIntError { kind: InvalidDigit })
Err("\"x\": invalid digit found in string")

The first error says what went wrong, but not which input it went wrong on. map_err swaps it for one that names the input. It can also change the error's type, here from ParseIntError to String, and section 3 shows why that matters.

Say it: if it failed, change the error into this.

3. and_then: a next step that can fail too

Why and_then(half) and not map(half)? Try it:

let nested = parse("8").map(half);
println!("{nested:?}");
halving 8
Ok(Ok(4))

map wraps whatever your closure returns in an Ok. half already returns a Result, so you get a Result inside a Result: Result<Result<i32, String>, String>. and_then doesn't wrap anything. Your closure's Result becomes the result, so there's only ever one Result, and an error from either function ends up in it.

That only works if they're the same kind of error. Here's a parse_raw that skips the map_err and returns str::parse's error as it comes:

fn parse_raw(s: &str) -> Result<i32, std::num::ParseIntError> {
    s.parse()
}

let r = parse_raw("8").and_then(half);
error[E0271]: expected `half` to return `Result<_, ParseIntError>`, but it returns `Result<i32, String>`

A Result has one error type, and and_then won't change it for you. That's the job map_err did inside parse: it made the error a String, like half's, before the two ever met.

Say it: if it worked, try this next, and keep whichever error comes first.

4. ok() and err(): keeping one side

Sometimes you don't want the error at all. ok() turns a Result into an Option: Ok(v) becomes Some(v), and an Err becomes None. err() keeps the other side. With filter_map, that splits a list in two:

let inputs = ["8", "x", "4", "y"];
let numbers: Vec<i32> = inputs.iter().filter_map(|s| parse(s).ok()).collect();
let errors: Vec<String> = inputs.iter().filter_map(|s| parse(s).err()).collect();
[8, 4]
["\"x\": invalid digit found in string", "\"y\": invalid digit found in string"]

So with ok(), the error goes nowhere. It's dropped, and nothing tells you it existed. That's exactly right when a bad input just means "skip it". It's a bug when you needed to know why.

Say it: the value if it worked, and never mind why if it didn't.

5. ok_or: an Option that needs an error

Going the other way, from Option to Result, there's no error to carry, because None doesn't say why. So you supply one:

let v: Vec<i32> = vec![];
let first = v.first().ok_or("empty list");
println!("{first:?}");
Err("empty list")

On vec![3, 4], the same line gives Ok(3), and "empty list" is never used.

Part 1's rule applies here unchanged. ok_or's argument is worked out before the call, every time. ok_or_else takes a closure, and runs it only on None. If building the error costs something, like a format!, give ok_or_else a closure that builds it.

Say it: the value if there is one, or fail with this.

6. ?: the error goes up

Here's the puzzle's chain again, written with ?:

fn half_of(s: &str) -> Result<i32, String> {
    let n = parse(s)?;
    let h = half(n)?;
    Ok(h * 10)
}

It prints exactly what the puzzle printed, halving lines included. ? asks the same question as and_then: did that work? If so, you get the value and the next line runs. If not, the function returns the error right there, and nothing after it runs.

So with ?, the error goes up, to whoever called you. It's how most Rust code passes errors along. ? is also a little more forgiving than and_then. On the way out, it converts the error with From, so it can turn a ParseIntError into your own error type for you. Rust Patterns #2 and #3 pick up from there.

Say it: if it worked, carry on. If it didn't, hand the error back to my caller.

Cheat sheet

You writeOn Ok / SomeWhere the error goes
r.map(f)runs fpast f, unchanged
r.map_err(f)passes it oninto f, which makes a new one
r.and_then(f)runs f, which can failpast f, or out of f
r.ok()gives Some(v)nowhere: it's dropped
o.ok_or(e)gives Ok(v)there wasn't one: e becomes the error
r?gives v, and carries onup to the caller

And the rule of thumb: every error goes somewhere. It's passed along, changed, dropped or sent up. Make sure the one you chose is the one you meant.

The whole series, in one question

Part 1 asked when the code you pass to a method runs, and the answer depended on whether there was a value. Part 2 asked the same thing of iterators, and the answer depended on what sat at the end of the chain. This part followed the error a Result carries instead of a value, and it went wherever you sent it.

All three come down to one habit. Before you hand your code to a method, ask when it will run. Before you let an error go, ask where it will end up.
