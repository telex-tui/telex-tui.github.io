When Does Your Code Run? Four Option Methods in Plain English

November 2026

Start with a puzzle. Here's a function that announces itself when it runs, and one Option handed to three methods. Before you read on, decide what this program prints.

fn noisy() -> i32 {
    println!("called");
    0
}

fn main() {
    let a = Some(5);
    let x = a.unwrap_or(noisy());
    let y = a.unwrap_or_else(noisy);
    let z = a.map(|v| {
        println!("mapping");
        v * 2
    });
    println!("{x} {y} {z:?}");
}

Hold on to your answer. We'll come back to it at the end.

Every example was compiled with rustc 1.97.0, edition 2024. Compiler errors are cut down to their key lines.

The question

Most Option methods take something from you: a value, or a closure. The useful thing to ask about each one is when does the code I pass in actually run?

Most of the time you can ignore that question. You can't once your code does something besides produce a value: printing, counting, allocating, writing a file. Those are side effects, and they're how you find out exactly when your code ran. That's why noisy prints.

1. is_some: runs nothing of yours

let name = Some(String::from("Ada"));
if name.is_some() {
    println!("got a name");
}
println!("{name:?}");
got a name
Some("Ada")

is_some only looks. It borrows the Option, answers true or false, and leaves it exactly as it was. That's why name can still be printed on the last line. You haven't passed it any code, so there's nothing of yours to run. is_none asks the opposite question.

Say it: is there a value in there?

2. map: runs your closure if there's a value, once

let name = Some(String::from("Ada"));
let len = name.map(|s| {
    println!("measuring {s}");
    s.len()
});
println!("{len:?}");
measuring Ada
Some(3)

map hands the value inside the Some to your closure, and whatever the closure returns becomes the new value. An Option<String> goes in, and an Option<usize> comes out.

The println! isn't part of that. It's a side effect: something the closure does on the way to returning s.len(). On None, map never calls the closure, so the side effect never happens either. And because an Option holds at most one value, the closure runs at most once.

One more thing about map: it takes the Option by value. Use name after mapping it, and the compiler stops you, then suggests the fix:

error[E0382]: borrow of moved value: `name`
3 |     let len = name.map(|s| s.len());
  |                    ---------------- `name` moved due to this method call
help: consider calling `.as_ref()` to borrow the value's contents

name.as_ref().map(|s| s.len()) gives map a reference to the value instead of the value itself, and name is still there afterwards.

Say it: if there's a value, turn it into this.

3. unwrap_or: your code ran before the method did

unwrap_or(x) gives you the value if there is one, or x if there isn't. Now look at what the puzzle passed it: noisy(). That isn't a closure. It's a call, and Rust works out a method's arguments before it calls the method. So noisy() runs first, prints called and returns 0, and unwrap_or is handed a plain 0. It never sees your code at all.

The puzzle's line means exactly this:

let fallback = noisy();
let x = a.unwrap_or(fallback);

Written that way, it's obvious that noisy runs whether a is Some or not. unwrap_or doesn't get to decide whether your code runs. By the time it's called, your code already has.

Say it: the value, or this one I've already worked out.

4. unwrap_or_else: runs your closure if there's no value, once

unwrap_or_else(f) takes a closure instead of a value, so it does get to decide. It calls f only when there's no value to give you.

In the puzzle it was handed noisy without parentheses: the function itself, not a call to it. A function can go anywhere a closure with the same shape can, so that's the same as unwrap_or_else(|| noisy()).

Say it: the value, or work one out if there isn't one.

This pair has a cost side too: why you'd rather not allocate a fallback you won't use. That's covered in Rust's _or Methods in Plain English. Side effects tell the same story, and they're easier to see.

Back to the puzzle

With a = Some(5), the program prints:

called
mapping
5 5 Some(10)

called comes from the unwrap_or line, because noisy() ran before unwrap_or did. unwrap_or_else had a value to give, so it never called noisy. map had a value too, so its closure ran once and printed mapping.

Now change the first line to let a: Option<i32> = None;:

called
called
0 0 None

Two calleds. The first comes from unwrap_or, exactly as before. The second comes from unwrap_or_else, which needed a fallback this time. There's no mapping, because there was nothing to map.

And the rule of thumb: if the code you pass in does something besides return a value, check whether it should run when there's no value, or when there is one.

What's not here

Result follows the same rules. is_ok, map, unwrap_or and unwrap_or_else behave just like their Option versions, except that unwrap_or_else passes the error into your closure.

Iterators have a map too, with one twist: it's lazy. Its closure runs once per item, but only when something pulls that item through the chain. So a side effect in an iterator's map might happen for every item, some of them or none at all. That's Inside an Iterator Chain's territory.

And if a side effect is all you want, map is the wrong tool. inspect lets you look at a value without changing it, and a plain if let or for loop says what you mean.
