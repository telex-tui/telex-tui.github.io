Inside an Iterator Chain, Part 4: Where the & Comes From

November 2026

Part 4 of 4 in Inside an Iterator Chain.

Previous: Part 3: Beyond One In, One Out | Next: none

Parts 1 to 3 kept references out on purpose. The source was a range, every value was a plain i32, and the slot-in rule could be seen on its own: a step fits when its input is the previous step's Item.

Here the values come from a Vec. That brings in ownership and references, but no new rule. Every & in this part is part of an item type, and the same rule handles it. The plus, times, minus and keep steps are the ones from parts 2 and 3.

1. into_iter() hands out the values, and gives up the Vec

let nums = vec![1, 2, 3, 4, 5];
let out: Vec<i32> = nums.into_iter().plus(1).times(3).minus(2).collect();
[4, 7, 10, 13, 16]

The items are plain i32, so plus fits, just as it did after a range. The cost is the Vec. into_iter takes it by value, so afterwards it's gone. Try to print nums and the compiler says, trimmed:

error[E0382]: borrow of moved value: `nums`
note: `into_iter` takes ownership of the receiver `self`, which moves `nums`

2. iter() hands out references, and the Vec stays

To keep the Vec, borrow it instead. iter() hands out an &i32 for each value, pointing at it where it sits.

let nums = vec![1, 2, 3, 4, 5];
let out: Vec<i32> = nums.iter().map(|n| n + 1).collect();
[2, 3, 4, 5, 6]

nums is still there afterwards. Inside the closure, n is an &i32, but the arithmetic hides it, because Rust implements + for &i32 too. Our own plus doesn't hide anything:

let out: Vec<i32> = nums.iter().plus(1).collect();
error[E0271]: expected `Iter<'_, {integer}>` to be an iterator that yields `i32`, but it yields `&{integer}`

That's the same error as putting the label too early in part 2. An &i32 isn't an i32, so the step doesn't fit.

3. filter adds a reference of its own

filter after iter() hands its test a reference to a reference:

let evens: Vec<&i32> = nums.iter().filter(|n| **n % 2 == 0).collect();
[2, 4]

Write n % 2 instead and the compiler names the type: it "cannot calculate the remainder of &&{integer} divided by {integer}". One & comes from iter(). The other comes from filter.

Why does filter lend the value instead of handing it over? Here's keep from part 3, with the i32 taken out so it works for any item:

impl<I, P> Iterator for Keep<I, P>
where
    I: Iterator,
    P: FnMut(&I::Item) -> bool,
{
    type Item = I::Item;

    fn next(&mut self) -> Option<I::Item> {
        loop {
            let item = self.inner.next()?;
            if (self.test)(&item) {
                return Some(item);
            }
        }
    }
}

The test only looks. If it took item, there would be nothing left to return. Part 3's keep could pass n by value only because an i32 copies for free: the test got a copy and the step kept the original. A String doesn't copy for free, so the test gets a reference:

let words = vec![String::from("bean"), String::from("cup"), String::from("roast")];
let long: Vec<String> = words.into_iter().keep(|w| w.len() > 3).collect();
["bean", "roast"]

Back to the numbers, and &&i32 adds up. iter() makes each item an &i32, and filter lends the test a reference to that. A pattern can peel both off at once: filter(|&&n| n % 2 == 0).

4. copied() turns references back into values, and it's just another step

let out: Vec<i32> = nums.iter().copied().plus(1).times(3).minus(2).collect();
[4, 7, 10, 13, 16]

copied() sits right after iter() and changes the Item from &i32 to i32. After that, every step from part 2 fits again, and nums is untouched.

It's the same shape as every other step. Here's our own, kept to i32 like the rest of the series:

impl<'a, I: Iterator<Item = &'a i32>> Iterator for Copied<I> {
    type Item = i32;

    fn next(&mut self) -> Option<i32> {
        let n = self.inner.next()?;
        Some(*n)
    }
}

'a names how long the borrowed values live. Apart from that, the step pulls a reference and hands on the value behind it. Our trait method is called copy_out, so it doesn't clash with the standard library's copied, and nums.iter().copy_out() gives the same output. For values that don't copy for free, cloned() is the same step with .clone() in place of *.

The whole series, in one rule

A chain is a set of steps. Each holds the step before it and answers next, one value at a time, when the consumer asks. A step slots in when its input type is the previous step's Item.

References don't change that. They're part of the Item. iter() puts one there, filter lends one to its test, and copied() takes one away. Each is the same rule, applied.
