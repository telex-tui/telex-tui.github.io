When Does Your Code Run? Part 2: Iterators

November 2026

Part 2 of 2 in When Does Your Code Run?

Previous: Part 1: Four Option Methods | Next: none

Part 1 asked one question about four Option methods: when does the code you pass in actually run? Option's map had the simplest answer: straight away, at most once.

Iterators have a map too. Same name, same question, different answer. Another puzzle first. Decide what this prints:

let v = vec![1, 2, 3];
let big: Vec<_> = v.iter()
    .map(|x| { println!("map {x}"); x * 10 })
    .filter(|x| { println!("filter {x}"); *x > 10 })
    .collect();
println!("{big:?}");

Hold on to your answer. Section 2 has it.

Every example was compiled with rustc 1.97.0, edition 2024. Compiler errors are cut down to their key lines.

1. Nothing runs until something asks

Start by taking something away. Here's the same chain without collect:

v.iter()
    .map(|x| { println!("map {x}"); x * 10 })
    .filter(|x| { println!("filter {x}"); *x > 10 });

Run it, and it prints nothing at all. Not one map line. The compiler saw this coming:

warning: unused `Filter` that must be used
  = note: iterators are lazy and do nothing unless consumed

Calling map doesn't call your closure. It wraps the iterator in a Map: a step that will call your closure later, each time it's asked for an item. filter wraps that in a Filter. Nothing has asked for an item, so nothing has run. Inside an Iterator Chain calls this a recipe, not a run.

You can watch the gap between building the chain and running it:

let chain = v.iter().map(|x| { println!("map {x}"); x * 10 });
println!("built the chain");
let out: Vec<_> = chain.collect();
built the chain
map 1
map 2
map 3

The closure was written on the first line, but it ran on the third.

Say it: when something asks for an item, run this on it.

2. One item at a time, all the way through

Here's what the puzzle prints:

map 1
filter 10
map 2
filter 20
map 3
filter 30
[20, 30]

If you expected three map lines and then three filter lines, you're in good company. But there's never a moment when map has finished and filter starts.

collect asks filter for an item. filter can't answer without one of its own, so it asks map. map asks v.iter() for 1, runs your closure, and hands 10 up to filter. filter's closure says no, so filter asks map again, and 2 makes the same trip. Each item goes all the way through the chain before the next one starts.

3. Stopping early

Swap collect for something that doesn't need every item:

let v = vec![1, 2, 3, 4, 5];
let first_big = v.iter()
    .map(|x| { println!("map {x}"); x * 10 })
    .find(|x| *x > 15);
println!("{first_big:?}");
map 1
map 2
Some(20)

find stops asking as soon as it has an answer. 3, 4 and 5 are never pulled, so your closure never sees them. take, any, all and position stop early the same way.

So a side effect in an iterator's map might happen for every item, some of them or none at all. What decides isn't map. It's whatever sits at the end of the chain.

4. Part 1's map, side by side

Option's mapAn iterator's map
When your closure runsstraight awaywhen something asks for an item
How many timesat most onceonce per item pulled
What it asks forFnOnceFnMut

The last row follows from the other two. An iterator's map calls your closure again and again, so it needs FnMut: a closure that can be called more than once, and can change what it captured between calls. That's what lets this count work:

let v = vec![1, 2, 3];
let mut count = 0;
let doubled: Vec<_> = v.iter().map(|x| { count += 1; x * 2 }).collect();
println!("{doubled:?} after {count} calls");
[2, 4, 6] after 3 calls

Option's map calls your closure once at most, so it asks for less: FnOnce, a closure that only has to work once. That lets it accept something an iterator's map can't, a closure that gives away what it captured:

let name = String::from("Ada");
let greeting = Some(1).map(|_| name);
println!("{greeting:?}");
Some("Ada")

Try the same closure on an iterator, and the compiler stops you:

let names: Vec<String> = v.iter().map(|_| name).collect();
error[E0507]: cannot move out of `name`, a captured variable in an `FnMut` closure
help: consider cloning the value if the performance cost is acceptable

The first call would give name away, and there'd be nothing left for the second. Same name, same question, two different answers, and the signatures say so. Rust Patterns #15: Fn, FnMut, FnOnce has more on the three closure traits.

5. When the side effect is the point

If you only want to watch values go past, inspect says so. It hands your closure a reference to each item and passes the item on unchanged:

let v = vec![1, 2, 3];
let total: i32 = v.iter()
    .inspect(|x| println!("saw {x}"))
    .map(|x| x * 10)
    .sum();
println!("{total}");
saw 1
saw 2
saw 3
60

inspect is lazy too: it runs when sum asks, not before. And if doing something is the whole job, a for loop is clearer than any chain. It runs once per item, straight away, and nobody reading it wonders whether it runs at all.

Cheat sheet

You writeYour closure runs
v.iter().map(f), and nothing elsenever
….map(f).collect()once per item, each item all the way through before the next
….map(f).find(p)once per item, until find has its answer
Some(x).map(f)straight away, once (part 1)

And the rule of thumb: in an iterator chain, the end of the chain decides when your code runs and how many times.
